# CLAUDE.md — бот-обменник xRocket ⇄ CryptoBot (exch)

Черновик для корня репозитория проекта. Источник правды — `SPEC.md`. Если код и SPEC расходятся — остановись и спроси, не «чини» SPEC молча.

## Что это

Telegram-бот на Rust: клиент присылает чек или счёт CryptoBot/xRocket, бот принимает деньги юзерботом (MTProto) и выплачивает через API кошелька. Деньги клиентов — в леджере с двойной записью. Подробно — SPEC §1–§4, архитектура — §10.

## Команды

```bash
# локальная БД (Windows: Docker Desktop; Linux: то же)
docker run -d --name exch-pg -e POSTGRES_PASSWORD=dev -p 5432:5432 postgres:16
export DATABASE_URL=postgres://postgres:dev@localhost:5432/exch   # PowerShell: $env:DATABASE_URL="…"

cargo fmt --all
cargo clippy --all-targets --all-features -- -D warnings
cargo test --all-features                  # нужен DATABASE_URL; sqlx::test создаёт БД на тест
cargo sqlx migrate run                     # миграции из migrations/
cargo sqlx prepare --workspace -- --all-targets   # после изменения SQL-запросов; коммитить .sqlx/
cargo run -p app -- --help                 # CLI: run | migrate | login --account <label> | selftest
```

Перед **каждым** коммитом все четыре: fmt, clippy без предупреждений, test, `sqlx prepare --check`.

## Карта крейтов (SPEC §10.2)

`domain` (деньги, FSM, цены, проводки; без IO) ← `parsers` ← `storage` ← `wallets` (трейты `WalletApi`, `WalletUserbot`, фейки под feature `fakes`) ← `userbot` (grammers) ← `tgbot` (frankenstein, UI) ← `engine` (FSM-драйвер, outbox, рекавери, сверка) ← `ops` (ops-бот) ← `app` (бинарник).
Зависимости только в эту сторону. В `domain` нет tokio, sqlx, reqwest.

## Правила, которые нельзя нарушать

### Деньги
1. Только `rust_decimal::Decimal`. `f32`/`f64` запрещены (`clippy.toml: disallowed-types`). В БД — `NUMERIC(38,18)`, в JSON к Crypto Pay — строки.
2. Округление (SPEC §10.4): выплата — вниз до `payout_step`; сумма к оплате — вверх; остаток округления — в пользу сервиса. Формулы — §2.3, не изобретать свои.
3. Любое движение денег = сбалансированная проводка в леджере (`ledger_transactions` + `ledger_entries`, сумма по активу = 0). Комиссия признаётся в момент выплаты. Леджер только дописывается.

### Двойные выплаты и потерянные чеки
4. Денежное действие = строка в `operations` (outbox), вставленная **в той же транзакции**, что и переход заявки. Сетевой вызов — только после коммита `status = 'dispatched'`.
5. Ключ идемпотентности = `operations.idempotency_key` = `spend_id` / `transferId` / `withdrawalId`. Формат: `ord-<id>-payout|refund|excess|pay|intake-<n>`, `rb-<id>`. Повтор — всегда с **тем же** ключом.
6. Действия юзербота без ключа идемпотентности (`pay_invoice`, инлайн-чеки) — `max_attempts = 1`. При неясном исходе — сверка или `MANUAL_REVIEW`, **никогда** повторное нажатие.
7. Переходы заявки — только через `domain::fsm::transition`. Таблица в коде = `order_state_transitions` в БД (это проверяет тест). Не добавляй переход в одном месте без другого и без обновления `diagrams/08-state-order.puml`.
8. Каждое сообщение от бота кошелька сохраняется в `wallet_messages` **до** разбора.
9. Не ослабляй уникальные индексы и CHECK в миграциях (`operations_one_settle_per_order`, `orders_intake_param_live`, `operations_check_once`, `ledger_tx_once_per_operation` и т. д.).

### Юзербот
10. Отправлять команды только ботам кошельков по **закреплённым peer ID** из конфига. Никогда не резолвить username из ссылки клиента. Не подписываться на каналы, не писать людям.
11. Одно денежное действие в полёте на аккаунт; не чаще 1 действия в 1,5 с; соблюдать FloodWait.
12. Незнакомый ответ кошелька → `Unknown` → автопауза направления + CRITICAL. Не подгоняй регулярку под один текст: добавь фикстуру в `parsers/tests/fixtures/<platform>/<case>/` и правило, которое не пересекается с другими классами.

### Секреты и логи
13. Токены, сессии, `SESSION_KEY`, пароли чеков — только из переменных окружения или памяти. Тип `secrecy::SecretString`. Не попадают в логи, ошибки, БД (кроме зашифрованной сессии), коммиты и тестовые снимки.
14. `start_param` чеков и адреса в логах — через `Masked<T>`.
15. `.env` никогда не коммитится; новые переменные — добавить в `.env.example` без значений и в SPEC §12, шаг 8.

### Интерфейс
16. Тексты — в `crates/tgbot/ui/ru.toml`, не в коде. Telegram HTML: только разрешённые теги, все подстановки экранированы. Денежный поток — обычные HTML-сообщения; rich — только справочные экраны, у каждого есть фолбэк (SPEC §6.1).
17. Каждая ошибка говорит, где деньги клиента и что делать (SPEC §6.3).

## Ошибки и стиль

- В библиотечных крейтах — `thiserror`, в `app` — `anyhow`. Не `unwrap()`/`expect()` вне тестов и инициализации (там — с понятным сообщением).
- Async: не блокировать рантайм (тяжёлое — `spawn_blocking`). Не держать транзакцию БД во время сетевого вызова.
- Логи — `tracing` со спанами `order_id`, `op_id`, `account`. Уровни: `error` = нужна реакция человека.
- Время — UTC (`chrono::DateTime<Utc>`), в UI — часовой пояс владельца или клиента.
- Новые зависимости — только с обоснованием в PR/коммите; grammers закреплён по `rev`.

## Тесты

- Не удаляй и не ослабляй тесты, чтобы они прошли. Если тест или требование SPEC неверны — остановись и напиши, почему.
- Денежная математика — `proptest`; FSM — табличные тесты; парсеры — фикстуры + `insta`; сценарии — `engine` + фейки кошельков + реальный PostgreSQL (`sqlx::test`).
- Любой новый сценарий с деньгами — тест на сбой «выполнил и вернул таймаут» и проверка: ≤ 1 внешний перевод на ключ, леджер сбалансирован, балансы фейков = леджер.
- `schema_test.sql` должен проходить после каждой миграции.

## Как работать по вехам (SPEC §14)

1. Прочитай `SPEC.md`, этот файл, `docs/PROGRESS.md`, `git log --oneline -30`.
2. Прогони тесты — должны быть зелёными до начала работы.
3. Составь план (файлы, интерфейсы, тесты) и **дождись «ок»**.
4. Делай маленькими шагами; каждый законченный шаг — коммит с понятным сообщением (`engine: retry payout with same spend_id after timeout`).
5. Не трогай то, что не относится к вехе.
6. В конце: обнови `docs/PROGRESS.md` (сделано / дальше / известные проблемы), покажи вывод тестов и clippy, список коммитов и что проверить руками.
7. Веха готова, когда выполнены её критерии приёмки из SPEC §14.1.

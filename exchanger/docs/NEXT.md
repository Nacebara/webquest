## Выжимка правил задания (полный текст — `OWNER-BRIEF.md`)

- Не верить документам: «сделано» — заявление. Вывод о коде — только по открытому коду, о живом
  поведении — только по логу, ответу Telegram или скриншоту владельца.
- Находка = доказательство (файл:строка, тест, живой ответ) + тяжесть 0–4 + сценарий с числами +
  что сделать + цена (S до 2 часов, M до дня, L больше). Помечать: «запуском», «вживую», «чтением».
- Доказать запуском можно временным тестом `crates/<крейт>/tests/zz_audit_<имя>.rs`: запустить,
  вывод — в находку, файл удалить. В конце `git status --short` пуст.
- Решение Р2 окончательное (только юзербот, API кошельков не предлагать). Docker для exch не
  предлагать. Схема базы — только новыми миграциями. Тесты не ослаблять.
- Противоречие документов — записать и спросить владельца, молча не чинить.
- Секреты не просить и не повторять. Git: коммит после шага, сразу отправка, без `--force`.
- Владельцу — по-русски, просто, сначала результат; вопросы — с вариантами и рекомендацией.

## Заход 4 — безопасность: что сделать

Вопрос захода: может ли посторонний, клиент или сотрудник сделать то, чего ему нельзя, и могут ли
утечь секреты.

Читать (прицельно): `crates/ops/src/lib.rs`, `cb.rs`, `actions.rs` (проверка роли на каждом
обработчике), `inbox.rs`, `nav.rs`; `crates/tgbot/src/handler.rs`, `orders.rs` (чьи заявки
открывает callback); `crates/ui/src/html.rs` и места подстановки пользовательского текста;
`crates/app/src/config.rs`, `telegram.rs`, `demo.rs`, `record.rs`; `crates/botapi/src/client.rs`
(что попадает в текст ошибки).

1. Таблица «действие пульта → минимальная роль по коду → строка проверки». Обработчики без
   проверки; может ли оператор повысить себя, добавить персонал, обойти «только владелец».
2. Клиент: callback с чужим номером заявки (карточка, «Детали», «Забрать», отмена счёта,
   «Вернуть деньги», история) — временным сквозным тестом на поддельном Bot API.
3. HTML: имя, username, вопрос в поддержку, заметка, причина бана, ответ кошелька в карточке
   заявки — экранируются ли в обычном и rich-HTML пульта; можно ли вставить `<tg-button>` или
   `<a href>` (доказать тестом).
4. Подтверждения: одноразовость, срок, привязка к сотруднику и параметрам; где стоит правило
   «расхождение больше 1 % — владелец» для «Деньги пришли» (М-5).
5. Ссылка «Забрать»: откуда берётся и проверяется ли, что она ведёт на бот кошелька.
6. Злоупотребления: лимиты ссылок и заявок, заморозка резерва счетами (М-7), флуд ссылками на
   счета (каждая — действие юзербота), спам в поддержку.
7. Секреты: токен в адресе Bot API и тексты ошибок; `.env.bak` в `.gitignore`; `exch record` и
   `listen` пишут живые ссылки; история git на шаблоны токенов (значения не цитировать).
8. Демо с боевым токеном и базой: что защищает от запуска `exch demo` на боевых данных.

## Правила экономии (лимит владельца кончается за 15–20 минут тяжёлой работы)

1. **Без субагентов.** Два запуска параллельных аудиторов сожгли лимит, не дав отчётов.
2. Не читать целиком `SPEC.md`, `LOVEC-PORTING.md`, `HANDOVER.md`, `PROGRESS.md`, `PLAN-v1.md`,

3. Код читать прицельно: поиск → нужные функции. Команды объединять, длинный вывод обрезать.
4. Скриншоты и картинки — только в заходах про интерфейс.
5. **Каждую подтверждённую находку сразу записывать** в `docs/AUDIT-2026-11-11.md`, раздел 2;
   коммит и отправка на GitHub — после каждых 2–3 находок. Обрыв не должен ничего стирать.
6. Заход заканчивается, когда пройден его чек-лист (или видно, что лимит на исходе): обновить этот
   файл, дописать 3–5 строк в `docs/PROGRESS.md`, закоммитить, отправить, коротко отчитаться владельцу.

## Выжимка правил задания (полный текст — `OWNER-BRIEF.md`)

- Не верить документам: «сделано» — заявление. Вывод о коде — только по открытому коду, о живом
  поведении — только по логу, ответу Telegram или скриншоту владельца.
- Находка = доказательство (файл:строка, тест, живой ответ) + тяжесть 0–4 + сценарий с числами +
  что сделать + цена (S до 2 часов, M до дня, L больше). Помечать: «запуском», «вживую», «чтением».
- Доказать запуском можно временным тестом `crates/<крейт>/tests/zz_audit_<имя>.rs`: запустить,
  вывод — в находку, файл удалить. В конце `git status --short` пуст.
- Решение Р2 окончательное (только юзербот, API кошельков не предлагать). Docker для exch не
  предлагать. Схема базы — только новыми миграциями. Тесты не ослаблять.
- Противоречие документов — записать и спросить владельца, молча не чинить.
- Секреты не просить и не повторять. Git: коммит после шага, сразу отправка, без `--force`.
- Владельцу — по-русски, просто, сначала результат; вопросы — с вариантами и рекомендацией.

## Заход 3 — кошельки и юзербот: что сделать

Вопрос захода: может ли ответ кошелька быть понят неверно (зачислено не то или не тому), и что
будет при FLOOD, сбросе сессии, смене текстов. Создание чека и поиск созданного уже прочитаны в
заходе 1 (`crates/userbot/src/flows/issue.rs` — в порядке, кроме М-1).

Читать (прицельно): `crates/parsers/src/replies.rs`, `amount.rs`, `links.rs`, `screens.rs`;
`crates/userbot/src/flows/conv.rs` (окно ответа, «чистый чат»), сценарий активации, `invoice.rs`;
`crates/mtproto/src/lib.rs` (в комментарии — список непроверенного вживую), `transport.rs` (FLOOD,
ошибки авторизации); `crates/app/src/wallet_log.rs`. Живые ответы —
`crates/parsers/tests/fixtures/live_wallet_replies.json` (выборочно, поиском).

1. Суммы — временным тестом: `$0.02`, `(0.09$)`, запятая, пробелы в тысячах, `1,000.50`,
   `0.021025`; может ли долларовая сумма попасть в USDT.
2. Классы ответов: правдоподобный текст, который ложно даёт «получено» (входящий перевод, оплата
   нашего счёта, уведомление о нашем чеке, английский интерфейс).
3. Окно ответа: чужой или поздний ответ в окне текущей команды; два чека подряд.
4. Ссылки: омоглифы, тестнет, пробел или перевод строки в параметре (инъекция в `/start`), длина.
5. Оплата счёта: сумма сверяется на каждом экране, денежное нажатие одно, новый получатель,
   код-пароль → человек.
6. FLOOD, сброс сессии, бан: что получает оператор (тревога или только строка в логе) и что с
   операциями. Темп действий и однообразие — что снизит риск блокировки аккаунта.
7. Незнакомый ответ → «неясно» и пауза во всех сценариях (чек, счёт, баланс); нигде не
   превращается в «не найден».
8. Сообщение кошелька сохраняется в `wallet_messages` до разбора.
9. Список непроверенного вживую → шаги для живого прогона владельцем (фаза 4).

## 1. Что за проект

Telegram-бот-обменник между двумя кошельками внутри Telegram: **CryptoBot** (`@send`) и **xRocket** (`@xrocket`). Валюта — USDT, курс 1:1, сервис берёт комиссию.

**Главное (решения владельца, DESIGN-v0.2 §1):**

- **Основной спрос — CryptoBot → xRocket.** Люди уходят из CryptoBot и забирают баланс в xRocket. Обратное направление — встречный поток, он пополняет сторону xRocket.
- **Вся работа — через юзербота.** Обычный аккаунт Telegram (MTProto) делает всё как человек: активирует чеки клиентов, создаёт чеки выплат, оплачивает счета. **API Crypto Pay и xRocket Pay не используются.** Кошелёк сервиса — личный баланс аккаунта юзербота, по одному на платформу (метки `cb`, `xr`).
- **Чеки с паролем не принимаем.** Логики паролей нет.
- **Чек создаётся как у обычного пользователя:** инлайн `@send 10usdt` / `@xrocket 10` → «Отправить» → сообщение-чек с URL-кнопкой (юзербот отправляет его себе в «Избранное» и берёт ссылку из кнопки). Запасной путь — меню бота: CryptoBot `/checks` → «Создать чек» → USDT → сумма → ссылка; xRocket `/cheques` → «Персональный» → «Создать чек» → USDT → сумма → ссылка.
- **Оплата счёта CryptoBot:** ссылка → кнопка валюты → «Оплатить» → мини-приложение Telegram → PIN (`CRYPTOBOT_PIN`). Протокол мини-приложения неизвестен, пока владелец не запишет HAR (раздел 8). До этого шаг делает оператор вручную (`PayOutcome::NeedsHuman`).
- **Активация чеков — по логике ловца lovec 0.4.3** (старый проект владельца): `messages.sendMessage("/start <код>")` боту, `no_webpage`, свой `random_id`; разбор ответа по словарям.
- **Интерфейс** — минималистичный: главное меню reply-клавиатурой, инлайн-кнопки, одно сообщение на заявку, которое правится по шагам.

### 1.1. Направления и комиссии (`schema.sql`, таблица `directions`)

| Код | Клиент присылает | Клиент получает | Комиссия | Пол / потолок рычага | Роль |
|---|---|---|---|---|---|
| `cb_to_xr_check` | чек CryptoBot | чек xRocket | 2,5 % (мин. 0,10) | 1,5 / 3,5 % | **основной** |
| `xr_to_cb_check` | чек xRocket | чек CryptoBot | 1,5 % (мин. 0,10) | 0,5 / 3,0 % | встречный, пополняет `xr` |
| `pay_cb_invoice` | чек xRocket | оплаченный счёт CryptoBot | 3,0 % (мин. 0,20) | 2,0 / 4,0 % | пополняет `xr` |
| `pay_xr_invoice` | чек CryptoBot | оплаченный счёт xRocket | 2,0 % (мин. 0,20) | 1,0 / 3,5 % | |

Лимиты по умолчанию: 2–300 USDT, новый клиент — до 100. Все направления в сиде закрыты (`is_open = FALSE`): открывает владелец.

Ценовой рычаг: `fee = clamp(base + k·(1 − available/target), floor, cap)`, `k = 0,75` (`domain::pricing::Lever`). Чем меньше денег на целевой стороне, тем дороже направление. Предложенные резервы: `xr` ≈ 1 200 $, `cb` ≈ 800 $ — **владелец ещё не подтвердил**.

## 4. Как запустить

Нужно: Rust 1.97 (закреплён в `rust-toolchain.toml`), Docker или локальный PostgreSQL 16, `sqlx-cli` 0.9.0.

```bash
cd exchanger
docker run -d --name exch-pg -e POSTGRES_PASSWORD=dev -p 5432:5432 postgres:16
export DATABASE_URL=postgres://postgres:dev@localhost:5432/exch
cargo install sqlx-cli --version 0.9.0 --locked --no-default-features --features postgres,rustls
cargo sqlx database create && cargo sqlx migrate run --source migrations

cargo fmt --all --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace --all-features          # 308 тестов; sqlx::test создаёт БД на каждый тест
cargo sqlx prepare --workspace --check -- --all-targets
```

- `--all-features` обязателен: тесты симулятора — за feature `sim`.
- Без БД: `SQLX_OFFLINE=true cargo build` (данные запросов в `.sqlx/`). После изменения SQL — `cargo sqlx prepare --workspace -- --all-targets` и коммит `.sqlx/`.
- Пока проект не задеплоен, схема меняется правкой `schema.sql` **и** байт-в-байт копии `migrations/0001_init.sql` (тест сверяет). После первого деплоя — только новые миграции.
- Вручную схема применяется так: `psql -1 -f schema.sql` (в файле нет `BEGIN/COMMIT`).
- Переменные окружения — `.env.example`. Для тестов нужен только `DATABASE_URL`.

### M2. Юзербот (сценарии, вход, запись ответов)

**M2.1. `userbot::flows::UserbotWallet<T: Transport>`** — реализация `WalletBot`. Главная задача проекта. Спецификация — DESIGN-v0.2 §4, LOVEC-PORTING §3, §8, §9.

- *Актор аккаунта:* одно действие в полёте; не чаще 1 действия в 1,5 с; при `FloodWait(d)` — пауза всего аккаунта на `d`, вызовы до её конца сразу получают `BotError::FloodWait`.
- *Корреляция:* подписка (`subscribe`) **до** отправки. Ответ — первое сообщение бота с id больше id нашей команды. Правки того же сообщения переклассифицируют. Промежуточное «обработка» ждёт дальше. `ClaimNotice` и `IncomingTransfer` не закрывают ожидание. Таймаут 30 с → `Unknown`. Каждое сообщение отдаётся наружу для сохранения в `wallet_messages` (колбэк или канал — до разбора).
- *`activate_check`:* `send_text(WalletBot(p), "/start <param>", tag.random_id)`. Повтор после таймаута транспорта — с тем же `random_id`; `RandomIdDuplicate` значит «уже отправлено», ждём ответ. xRocket: «не найден» на свежем чеке → один повтор (правило lovec: только если чек моложе 3 с).
- *`issue_check` инлайн:* `inline_query(p, "97.5usdt" | "97.5")` → результат с USDT и ровно этой суммой → `send_inline(SavedMessages, …, tag.random_id)` → ссылка из URL-кнопки → `parsers::replies::parse_created_check` → `Issued{method: Inline}`. Ошибка до `send_inline` → меню. Ошибка или таймаут после → `Unknown` (меню **нельзя**: чек мог создаться).
- *`issue_check` меню:* CryptoBot `/checks` → «Создать чек» → USDT → сумма → ссылка; xRocket `/cheques` → «Персональный» → «Создать чек» → USDT → сумма → ссылка. Кнопки — по тексту (словарь синонимов), не по позиции. «Недостаточно средств» → `InsufficientFunds`. Любая неясность после ввода суммы → `Unknown`.
- *`find_issued_check`:* `history(SavedMessages)` — сообщение `via_bot = p` с суммой после времени операции; затем список чеков бота («Мои чеки»). Несколько кандидатов → `None` и человек.
- *`inspect_invoice`:* `/start IV…` или `inv_…` → `parse_invoice_card`.
- *`pay_invoice`:* карточка → кнопка валюты USDT → «Оплатить» → у CryptoBot кнопка web app → `open_webapp` → **`NeedsHuman`** (до HAR владельца). У xRocket — по ответу бота. Любая неясность после «Оплатить» → `Unknown`. Повторного нажатия нет никогда.
- *`balances`:* экран «Кошелёк» → `parse_balance`.

*Тесты* (`crates/userbot/tests/flows.rs` против `sim`): каждый путь и каждый класс ответа; каждый сбой из `Fault` на каждом шаге; инварианты: на один `random_id` не больше одного созданного чека; `Unknown` ни в одном сценарии не ведёт к повторному созданию или оплате; FLOOD_WAIT ставит на паузу весь аккаунт; правка «обработка» → «вы получили» даёт `Received`; входящий перевод во время ожидания не считается выигрышем.
*Готово, когда* всё это зелёное и `WalletBot` реализован полностью (`pay_invoice` для CryptoBot заканчивается `NeedsHuman`, в симуляторе шаг PIN покрыт отдельным тестом через `SimWorld::complete_webapp_payment`).

**M2.2. Хранение сессии и `exch login`.** `SessionStore` для `mtproto` поверх таблицы `userbot_accounts` (`session_ciphertext`, `session_nonce`, `key_version`). Команда `exch login --label ub-cb-1` (телефон и код — из терминала, через `mtproto::TerminalPrompt`; телефон в БД только маской). Привязка к `wallet_accounts` (`storage::wallets::ensure_wallet`).
*Готово, когда* тест с `MemoryStore` → БД проходит, секреты не попадают в логи (тест на `Debug` и `tracing`).

**M2.3. Режим записи и `exch selftest`.** `exch record --label …` — подключиться, ничего не отправлять, сохранять всё от @send/@xrocket в `wallet_messages` и в JSON-файл (для фикстур). `exch selftest` — проверка на живом аккаунте: сверка ботов, баланс, активация своего чека на 1 USDT, инлайн-чек на 1 USDT.
*Готово, когда* команды есть и протестированы на `sim`. Живой прогон — у владельца.

### M3. Движок (`crates/engine`) и недостающее хранилище

**M3.1. Репозитории `storage`.**

- `operations`: создать вместе с переходом заявки, в одной транзакции (`random_id` — в `request`); `dispatch` (status `dispatched`, `attempts + 1`, коммит **до** действия юзербота); `finish` (`succeeded`/`failed`/`unknown` + `response`, `external_id`); очередь `FOR UPDATE SKIP LOCKED` по `operations_due` + `LISTEN/NOTIFY`.
- `holds`: place / shrink / consume / release под `pg_advisory_xact_lock` по кошельку; проверка `available ≥ amount`.
- `wallet_messages`: вставка до разбора (уникальность по `(userbot, bot, message_id, edit_date)`), `parsed_kind`, `operation_id`.
- `wallet_chat_cursors`, `reconciliations`, `settings` (типизированные), `staff`/`bans`, `alerts` (дедупликация открытых), `admin_audit`.

*Готово, когда* есть тесты на живом PostgreSQL на каждый уникальный индекс и CHECK (второй settle на заявку, второй `activate_check` того же чека, вторая оплата счёта, `max_attempts > 1` у выплаты — всё отклоняется).

**M3.2. FSM-драйвер.** `Engine::handle(order_id, Event)`: загрузить заявку `FOR UPDATE` → `domain::fsm::transition` → в одной транзакции применить эффекты (`Operation` → строка outbox, `Hold` → holds, `Post` → проводка по шаблону `domain::ledger`) и записать переход. Котировка (`domain::pricing`) фиксируется в `OrderPatch` при `Received`.

**M3.3. Исполнитель операций (outbox-воркер).** Берёт `pending`, ставит `dispatched`, коммит, вызывает `WalletBot` по `platform`, пишет результат и шлёт событие в FSM. Таблица соответствия:

| Результат | Событие |
|---|---|
| `ActivationOutcome::Received(m)` | `CheckActivated{fully_funded}` (сумма из ответа, а не из ссылки) |
| `Rejected(_)` | `CheckRejected` |
| `Unknown` | `IntakeOutcomeUnknown` |
| `IssueOutcome::Issued` | `PayoutConfirmed` / `RefundConfirmed` (+ `payout_check_url`) |
| `InsufficientFunds` | `PayoutFailed` / `RefundFailed` + автопауза направления |
| `IssueOutcome::Unknown` | сверка `find_issued_check` → Confirmed / Failed |
| `PayOutcome::Paid`, `AlreadyPaid`* | `InvoicePaid` (*`AlreadyPaid` — только если по сверке платили мы) |
| `Expired` | `InvoiceUnpayable` |
| `NeedsHuman`, `PayOutcome::Unknown` | `InvoicePayNeedsHuman` |
| `BotError::FloodWait` / `Unavailable` | операция не начиналась: назад в `pending` с `next_attempt_at` (не тратит попытку) |

**M3.4. Восстановление после рестарта.** Операции в `dispatched` на старте: `activate_check` → догнать историю чата (`history` от курсора) и разобрать; выводящие деньги → **никогда не повторять**, только сверка (`find_issued_check`, статус счёта) → событие или `ManualReview`.

**M3.5. Сверка и резервы.** Периодически `balances()` по каждому кошельку → сравнение с леджером (`reconciliations`, допуски из `settings.reconcile_tolerance`; при операциях в полёте — `skipped_inflight`). Расхождение выше `pause` → автопауза направлений, CRITICAL. Правило «не принимаем, если не можем выплатить» (`max_order_effective`), рычаг комиссии, автопауза при `critical`.

**M3.6. Таймеры.** Истечение котировки счёта (`quote_ttl_seconds`), таймаут `IntakeUnknown`, напоминания по `ManualReview`.

*Готово, когда* сценарные тесты `engine` + `UserbotWallet<SimTransport>` + PostgreSQL проходят для П1 (CB → XR), П2 (XR → CB), оплаты счёта с недоплатой и переплатой, возврата, всех отказов чека. **Crash-тест:** точки отказа (failpoints) между каждым шагом «коммит → действие → результат», 200 итераций со случайными сбоями: ≤ 1 созданный чек на операцию, ≤ 1 оплата на счёт, леджер сбалансирован, балансы `SimWorld` = леджер.

## 6. Денежные инварианты — нельзя ослаблять

1. Деньги — только `Decimal`; `f32/f64` запрещены линтером.
2. Каждое движение денег — сбалансированная проводка; леджер, журнал переходов и аудит только дописываются (триггеры).
3. Переход заявки + строка outbox — одна транзакция. Действие юзербота — только после коммита `dispatched`. Транзакция БД не держится во время действия юзербота.
4. **Выводящие деньги операции — одна попытка** (CHECK в схеме). Неясный исход → сверка или человек. Повторить можно только `activate_check`, `open_invoice`, `read_balance`.
5. `random_id` назначается до первой отправки и хранится в операции; любой повтор отправки — с ним же.
6. Уникальные индексы: одна живая расчётная операция на заявку, один чек — одна активация, один счёт — одна оплата, одна проводка на операцию.
7. Сумма прихода — из ответа бота, не из ссылки и не со слов клиента.
8. Не принимаем, если не можем выплатить (hold на целевой резерв до активации).
9. Писать только закреплённым ботам по peer ID; username из ссылки клиента не резолвить.
10. Незнакомый ответ → `Unknown` → автопауза + CRITICAL, а не угадывание.

Любое изменение, которое трогает эти пункты, — сначала тест, который доказывает, что инвариант держится, и описание в коммите.

## 8. Открытые вопросы и риски

- **PIN в мини-приложении.** MTProto даёт только URL web view; дальше — HTTP мини-приложения CryptoBot. Варианты: повторить его запросы по HAR (быстро, хрупко) или headless-браузер (тяжело). До решения — оператор.
- **Создаётся ли инлайн-чек при запросе.** Если чек создаётся уже на `getInlineBotResults`, нужен другой путь (меню) — иначе каждая подсказка списывает деньги.
- **Непривязанные чеки выплат.** Ссылку может забрать любой, у кого она есть. Ссылку отправляем только в личку клиенту. Стоит проверить, можно ли в меню CryptoBot/xRocket привязать чек к пользователю (если да — делать).
- **Незабранные чеки.** Деньги клиента лежат в чеке. Нужен отчёт ops «чеки, не забранные N дней» и процедура отзыва с возвратом.
- **Тексты ботов меняются.** Защита — `Unknown` → пауза, `wallet_messages` и быстрое добавление фикстур.
- **Бан аккаунта юзербота.** Выделенные аккаунты, лимиты частоты, не писать людям; резервный аккаунт и процедура переключения `wallet_accounts.is_active`.
- **grammers 0.10 живьём не проверен.** Сторож соединения и таймауты — на уровне приложения (см. `mtproto::transport`); первым делом — `exch selftest`.

## 9. Безопасность

- Токены ботов, строки сессий, `SESSION_KEY`, `TG_API_HASH`, `CRYPTOBOT_PIN`, коды входа — **только в переменных окружения на сервере**. Не в промтах, не в чатах с ИИ, не в логах, не в коммитах, не в тестовых снимках.
- Сессии юзерботов в БД — только зашифрованные (`mtproto::crypto`), ключ — `SESSION_KEY` (32 байта, `openssl rand -base64 32`).
- Телефоны — только маской. Ссылки на чеки в логах — маскировать.
- HAR-файл содержит PIN и токены мини-приложения: хранить вне репозитория, удалить после разбора.
- Код старого проекта lovec — только как справочник (читать, не запускать).

## 11. Словарь

| Термин | Значение |
|---|---|
| Юзербот | Обычный аккаунт Telegram, которым программа управляет через MTProto |

| Сверка | Сравнение баланса кошелька (экран бота) с леджером |
| `ManualReview` | Заявка ждёт оператора: автоматика не уверена, что произошло с деньгами |
| lovec | Старый проект владельца — ловец чеков; источник логики активации и словарей |

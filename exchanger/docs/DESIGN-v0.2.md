# DESIGN v0.2 — только юзербот

Решения владельца (7 октября 2026) поверх SPEC v0.1. Где SPEC и этот файл расходятся, прав этот файл; SPEC обновляется следом.

## 1. Решения

| # | Решение | Что меняется |
|---|---|---|
| Р1 | **Основной спрос — CryptoBot → xRocket.** Люди уходят из CryptoBot и забирают баланс в xRocket | Комиссии: `cb_to_xr_check` 2,5 % (основной), `xr_to_cb_check` 1,5 % (встречный, пополняет сторону xRocket). Резерв выплат больше на стороне xRocket |
| Р2 | **Вся работа — через юзербота.** Принимать, создавать чеки и оплачивать счета — обычным аккаунтом, как человек. | Р3 | **Чеки с паролем не принимаем** | Отказ «чек с паролем не принимаем, деньги остались в чеке». Состояния, события и таблицы для паролей удалены |
| Р4 | **Оплата счёта CryptoBot:** ссылка → кнопка валюты → «Оплатить» → мини-приложение Telegram → PIN | Сценарий `pay_invoice` с шагом мини-приложения; PIN — секрет окружения `CRYPTOBOT_PIN` |
| Р5 | **Создание чека — как обычный пользователь.** Основной путь: инлайн `@send 10usdt` / `@xrocket 10` → «Отправить» → сообщение-чек с кнопкой. Запасной: CryptoBot `/checks` → «Создать чек» → валюта → сумма → ссылка; xRocket `/cheques` → «Персональный» → «Создать чек» → USDT → сумма → ссылка | `issue_check`: сначала инлайн в «Избранное» (ссылка — из кнопки сообщения), иначе меню. | Р6 | **Красивый минималистичный интерфейс:** вся разметка, инлайн- и клавиатурные кнопки, главное меню | Клиентский бот с reply-клавиатурой главного меню и инлайн-кнопками в сообщениях (раздел 6) |
| Р7 | **Логика ловца — из lovec 0.4.3** | Активация, разбор ответов, форматы ссылок и уроки аудитов — из lovec (раздел 3) |

## 2. Деньги и безопасность — что не меняется

- Только `Decimal`; леджер с двойной записью; комиссия признаётся при выплате; FSM с охраной переходов в БД (31 переход).
- Каждая денежная операция — строка `operations` в одной транзакции с переходом заявки, затем действие юзербота.
- **Операции, которые выводят деньги** (`create_payout_check`, `create_refund_check`, `create_excess_check`, `pay_invoice`, `withdrawal`) — `max_attempts = 1` (CHECK в схеме). При неясном исходе — сверка (`find_issued_check`, статус счёта, баланс) или человек. Вслепую не повторяем.
- **`random_id`.** Каждой операции юзербота заранее назначается `random_id` (хранится в `operations.request`). Повтор отправки внутри попытки — только с ним: Telegram не создаёт второе сообщение (`RANDOM_ID_DUPLICATE`, факт lovec `tests/send_outcomes.rs`). Для инлайн-чека это означает: повтор `sendInlineBotResult` с тем же `random_id` не создаст второй чек [допущение M0: проверить, что CryptoBot и xRocket создают чек при отправке результата, а не при инлайн-запросе].

## 4. Архитектура юзербота

```
engine ──► userbot::WalletBot (трейт операций кошелька)
              │  реализация: userbot::flows::UserbotWallet<T: Transport>
              ▼
           userbot::Transport (трейт)
              ├─ mtproto::GrammersTransport — настоящий аккаунт (grammers 0.10.0, crates.io)
              └─ userbot::sim::SimTransport — симулятор @send и @xrocket для тестов
```

- **Контракты** — `crates/userbot/src/transport.rs`, `crates/userbot/src/wallet.rs`, API `crates/parsers`. Менять сигнатуры можно только вместе со всеми пользователями; добавлять — можно.
- **Актор аккаунта:** одно денежное действие в полёте; не чаще 1 действия в 1,5 с (`governor`); FLOOD_WAIT — пауза аккаунта и `BotError::FloodWait`.
- **Корреляция:** подписка на поток сообщений до отправки; ответ — первое финальное сообщение бота с id больше id нашей команды; правки того же сообщения обновляют классификацию; посторонние классы (`ClaimNotice`, `IncomingTransfer`) не закрывают ожидание, но сохраняются.
- **Сценарии (`flows`):**
  1. `activate_check`: `/start <код>` → ответ → `ActivationOutcome`. Для xRocket — один повтор при «не найден» на свежем чеке, с тем же или новым `random_id` по правилу lovec.
  2. `issue_check` (инлайн): `inline_query("10usdt")` у @send или `inline_query("10")` у @xrocket → выбрать результат с USDT и нужной суммой → `send_inline(SavedMessages, …, random_id)` → ссылка из URL-кнопки сообщения → `IssuedCheck`. Не получилось до отправки — переход к меню. Ошибка после отправки (исход неизвестен) — `Unknown`, без меню.
  3. `issue_check` (меню): CryptoBot `/checks` → «Создать чек» → валюта USDT → сумма → ссылка из ответа; xRocket `/cheques` → «Персональный» → «Создать чек» → USDT → сумма → ссылка. Нажатия — по тексту кнопок.
  4. `find_issued_check`: поиск в «Избранном» (сообщение через бота с суммой после времени операции) и в списке чеков бота.
  5. `inspect_invoice`: `/start IV…` или `/start inv_…` → карточка счёта.
  6. `pay_invoice`: открыть счёт → кнопка валюты (USDT) → «Оплатить» → для CryptoBot кнопка мини-приложения → `open_webapp` → ввод PIN. Протокол мини-приложения неизвестен до записи владельцем (см. раздел 8) — пока результат `NeedsHuman` и задача оператору; в симуляторе шаг PIN моделируется.
  7. `balances`: экран «Кошелёк».

## 5. Симулятор (`userbot::sim`)

Детерминированная модель двух ботов на общем «мире» (балансы аккаунтов, реестр чеков и счетов):
- `/start <чек>`: ответы всех классов из раздела 3 (успех, уже активирован, не найден, не для вас, подписка, капча, пароль); у xRocket — «не найден» на свежем чеке с успехом на повторе;
- инлайн-режим: `10usdt` / `10` → результаты по активам; отправка результата создаёт чек и сообщение с URL-кнопкой; дубль `random_id` → `RandomIdDuplicate`;
- меню чеков обеих платформ, нажатия кнопок, ввод суммы, «недостаточно средств»;
- счета: карточка, выбор валюты, «Оплатить», мини-приложение с PIN, статусы оплачен/истёк;
- уведомления «Ваш чек активировал @…», входящие переводы;
- сбои по сценарию теста: таймаут после выполнения, разрыв, FLOOD_WAIT, незнакомый текст, задержка ответа, промежуточное «обработка».

## 6. Интерфейс клиента

- **Главное меню** (reply-клавиатура, `is_persistent`, `resize_keyboard`):
  - `💱 Обменять чек` · `🧾 Оплатить счёт`
  - `📈 Курс и лимиты` · `📜 История`
  - `💬 Поддержка`

  При Premium у владельца — `icon_custom_emoji_id` вместо эмодзи в тексте кнопки; стиль `primary` у главных действий.
- Главный сценарий без меню: ссылка на чек или счёт в любой момент запускает заявку. Меню нужно, чтобы объяснить, что прислать.
- «Обменять чек» → сообщение с двумя направлениями и текущей комиссией → инлайн-кнопки `CryptoBot → xRocket` (`style: primary`), `xRocket → CryptoBot` → инструкция «пришлите чек CryptoBot на сумму от X до Y» с кнопкой «Как создать чек» (`@send 10usdt`) и «Отмена».
- Одно сообщение на заявку, правится по шагам. Итог выплаты: «Ваш чек xRocket на 97.50 USDT» + кнопки `Забрать чек` (url, `success`) и `Скопировать ссылку` (`copy_text`).
- Разметка: `<b>`, `<i>`, `<code>`, `<blockquote>`, `<blockquote expandable>`, `<tg-spoiler>`, `<tg-emoji>`, `<tg-time>`. Справочные экраны — rich message с HTML-фолбэком по образцу lovec (`Doc { rich, html }`). Денежный поток — обычный HTML.
- Bot API — тонкий клиент на `reqwest` по образцу lovec `bot_call` (JSON, `ok`/`description`/`retry_after`), с полями 10.3: `style`, `icon_custom_emoji_id`, `copy_text`, `rich_message`.
- Тексты — без канцелярита, каждая ошибка говорит, где деньги и что делать.

## 7. Тестирование

- Сценарии юзербота × симулятор: каждый путь из раздела 4, каждый класс ответа, каждый сбой.
- Денежные инварианты в сценариях: один `random_id` — не больше одного созданного чека; `Unknown` никогда не превращается в повтор создания.
- Движок (следующий этап) тестируется через `UserbotWallet<SimTransport>` и реальный PostgreSQL.
- Живые тесты на аккаунтах владельца — команда `exch selftest` (позже), из этой среды недоступно: сеть к Telegram закрыта.

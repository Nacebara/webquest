Решения владельца (7 октября 2026) поверх SPEC v0.1. Где SPEC и этот файл расходятся, прав этот файл; SPEC обновляется следом.

## 2. Деньги и безопасность — что не меняется

- Только `Decimal`; леджер с двойной записью; комиссия признаётся при выплате; FSM с охраной переходов в БД (31 переход).
- Каждая денежная операция — строка `operations` в одной транзакции с переходом заявки, затем действие юзербота.
- **Операции, которые выводят деньги** (`create_payout_check`, `create_refund_check`, `create_excess_check`, `pay_invoice`, `withdrawal`) — `max_attempts = 1` (CHECK в схеме). При неясном исходе — сверка (`find_issued_check`, статус счёта, баланс) или человек. Вслепую не повторяем.
- **`random_id`.** Каждой операции юзербота заранее назначается `random_id` (хранится в `operations.request`). Повтор отправки внутри попытки — только с ним: Telegram не создаёт второе сообщение (`RANDOM_ID_DUPLICATE`, факт lovec `tests/send_outcomes.rs`). У нажатия кнопки такой защиты нет: денежную кнопку нажимаем один раз, неясный исход — сверка или человек.

## 4. Архитектура юзербота

```
engine ──► userbot::WalletBot (трейт операций кошелька)
              │  реализация: userbot::flows::UserbotWallet<T: Transport>
              ▼
           userbot::Transport (трейт)
              ├─ mtproto::GrammersTransport — настоящий аккаунт (grammers 0.10.0, crates.io)
              └─ userbot::sim::SimTransport — симулятор @send и @xrocket для тестов
```

- **Контракты** — `crates/userbot/src/transport.rs`, `crates/userbot/src/wallet.rs`, API `crates/parsers`. Менять сигнатуры можно только вместе со всеми пользователями; добавлять — можно.
- **Актор аккаунта:** одно денежное действие в полёте; не чаще 1 действия в 1,5 с (`governor`); FLOOD_WAIT — пауза аккаунта и `BotError::FloodWait`.
- **Корреляция:** подписка на поток сообщений до отправки; ответ — первое финальное сообщение бота в окне команды (id больше id команды, меньше id нашего следующего сообщения); правки того же сообщения обновляют классификацию; посторонние классы (`ClaimNotice`, `IncomingTransfer`) не закрывают ожидание, но сохраняются. Меню ботов отвечают и правкой своего экрана (xRocket на сумму чека правит сообщение меню, оно старше суммы): окно такого ожидания открывает команда меню, закрывает наше следующее сообщение после суммы; правка экрана меню после команды считается ответом и для проверки «чистого чата».
- **Сценарии (`flows`):**
  1. `activate_check`: `/start <код>` → ответ → `ActivationOutcome`. Для xRocket — один повтор при «не найден» на свежем чеке, с тем же или новым `random_id` по правилу lovec.
  2. `issue_check` (меню, Р5): метка операции в «Избранном» → CryptoBot `/checks` → «Создать чек» → USDT → сумма → чек новым сообщением или «Пропустить ›» → чек; xRocket `/cheques` → «Персональный» → «Создать чек» → USDT → сумма → правка меню «подтвердите» → сверка суммы → «✅ Подтверждаю» → чек. Нажатия — по тексту кнопок. После действия, которое могло создать чек, — только `Unknown` и сверка.
  3. `find_issued_check`: экран чека в чате бота между меткой этой операции и меткой следующей, перед которым стоит наше сообщение из окна операции (команда меню или сумма).
  4. `inspect_invoice`: `/start IV…` или `/start inv_…` → первый экран счёта → карточка (статус, номер, сумма, фиат, «денег мало»).
  5. `pay_invoice` (Р4, Р12): открыть счёт → монета (CryptoBot) или способ «xRocket» → экран подтверждения с суммой → сверка → «Оплатить»; у CryptoBot для нового получателя — ещё «💸 Отправить платеж получателю». Каждое денежное нажатие — одно. Код-пароль → `NeedsHuman`.
  6. `balances`: экран «Кошелёк» (`/wallet`), у CryptoBot — сумма «Доступно» при удержании.

## 5. Симулятор (`userbot::sim`)

Детерминированная модель двух ботов на общем «мире» (балансы аккаунтов, реестр чеков и счетов):
- `/start <чек>`: ответы всех классов из раздела 3 (успех, уже активирован, не найден, не для вас, подписка, капча, пароль); у xRocket — «не найден» на свежем чеке с успехом на повторе;
- тексты и экраны — живые, из записи владельца (тест `same_as_live` сверяет их с записью символ в символ); у каждого сообщения бота — свой экран, callback-данные — как у живых ботов (`create`, `count-1`, `Success`, `Pay`);
- меню чеков обеих платформ (Р5): мультичек CryptoBot и «Пропустить ›», подтверждение xRocket правкой меню, «недостаточно средств», удаление чека (у xRocket — молча); дубль `random_id` → `RandomIdDuplicate`;
- счета обеих платформ (Р12): выбор монеты, способ оплаты, подтверждение, «Выберите сеть…», доверие новому получателю, «⏱ Загрузка» и квитанция; у CryptoBot — «лимит без код-пароля» за 24 часа: сверх него бот просит код и ничего не списывает (Р4, Р11); статусы оплачен/истёк;
- уведомления «Ваш чек активировал @…», входящие переводы;
- сбои по сценарию теста: таймаут после выполнения, разрыв, FLOOD_WAIT, незнакомый текст, задержка ответа, промежуточное «обработка»; отдельно — на нажатии, которое создаёт чек (`Call::CheckPress`) или платит (`Call::PayPress`).

## 6. Интерфейс клиента

- **Главное меню** (reply-клавиатура, `is_persistent`, `resize_keyboard`):
  - `💱 Обменять чек` · `🧾 Оплатить счёт`
  - `📈 Курс и лимиты` · `📜 История`
  - `💬 Поддержка`

  При Premium у владельца — `icon_custom_emoji_id` вместо эмодзи в тексте кнопки; стиль `primary` у главных действий.
- Главный сценарий без меню: ссылка на чек или счёт в любой момент запускает заявку. Меню нужно, чтобы объяснить, что прислать.
- «Обменять чек» → сообщение с двумя направлениями и текущей комиссией → инлайн-кнопки `CryptoBot → xRocket` (`style: primary`), `xRocket → CryptoBot` → инструкция «пришлите чек CryptoBot на сумму от X до Y» с кнопкой «Как создать чек» (`@send 10usdt`) и «Отмена».
- Одно сообщение на заявку, правится по шагам. Итог выплаты — **по утверждённому макету B1** (6 ноября 2026, заменяет прежний вариант с «Скопировать ссылку»): «✅ 97.50 USDT ждут вас в xRocket» + `Забрать` (url, `success`), ниже `Детали` (то же сообщение раскрывает «Получено · комиссия», номер заявки и время; `Скрыть` сворачивает) и `Ещё обмен`.
- Разметка: `<b>`, `<i>`, `<code>`, `<blockquote>`, `<blockquote expandable>`, `<tg-spoiler>`, `<tg-emoji>`, `<tg-time>`. Справочные экраны — rich message с HTML-фолбэком по образцу lovec (`Doc { rich, html }`). Денежный поток — обычный HTML.
- Bot API — тонкий клиент на `reqwest` по образцу lovec `bot_call` (JSON, `ok`/`description`/`retry_after`), с полями 10.3: `style`, `icon_custom_emoji_id`, `copy_text`, `rich_message`.
- Тексты — без канцелярита, каждая ошибка говорит, где деньги и что делать.

## 7. Тестирование

- Сценарии юзербота × симулятор: каждый путь из раздела 4, каждый класс ответа, каждый сбой.
- Денежные инварианты в сценариях: один `random_id` — не больше одного созданного чека; `Unknown` никогда не превращается в повтор создания.
- Движок (следующий этап) тестируется через `UserbotWallet<SimTransport>` и реальный PostgreSQL.
- Живые тесты на аккаунтах владельца — команда `exch selftest` (позже), из этой среды недоступно: сеть к Telegram закрыта.

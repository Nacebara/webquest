Решения владельца от 7 октября 2026 (DESIGN-v0.2, Р1–Р7) поменяли основу v0.1.

|---|---|---|

## Сводка

1. **Продукт.** Telegram-бот: прислал чек или ссылку на счёт — получил результат. Обмен чеков USDT CryptoBot ⇄ xRocket и оплата чужих счетов одного кошелька деньгами из другого. Условия видны до отправки денег, после — итог с разбивкой.
2. **Спрос.** Основной поток — CryptoBot → xRocket: люди уходят из CryptoBot и забирают баланс в xRocket (Р1). Встречный поток xRocket → CryptoBot и оплата счетов CryptoBot деньгами из xRocket пополняют сторону xRocket.
3. **Как работает.** Всё делает юзербот — обычный выделенный аккаунт Telegram через MTProto, по одному на платформу. Он активирует чек клиента командой `/start <код>`, создаёт чек выплаты на другой платформе (инлайн `@xrocket 97.5` или `@send 97.5usdt` → сообщение-чек в «Избранном» → ссылка из кнопки) и оплачивает чужие счета. Клиент получает ссылку и забирает чек одной кнопкой. Кошелёк сервиса — личный баланс аккаунта юзербота (`cb`, `xr`).
4. **MVP** = вехи M0–M5 и пилот M6 (§14): USDT, обмен чеков в обе стороны, оплата счетов (CryptoBot — пока руками оператора), базовая админка, логи по темам, сверка балансов, ручной разбор. Уже готово: фундамент (M1), доменная модель и схема БД v0.2, парсеры, симулятор кошельков, MTProto-транспорт, клиент Bot API, экраны клиента. Следующее — сценарии юзербота (M2.1).
5. **Экономика (базовый сценарий).** 40 обменов в день по 25 $, оборот 30 000 $ в месяц. Комиссия 2,5 % в основном направлении и 1,5 % во встречном, средняя 2,2 % — это 660 $ валовой прибыли. Платформы за активацию и создание чеков не берут [допущение M0]. Чистая прибыль — около 560 $ в месяц после сервера, Premium, ребалансировки и ожидаемых потерь от заморозок. Безубыточность — около 4 000 $ оборота в месяц (≈ 5 обменов в день). Оборотный капитал — 2 000 $: xRocket ≈ 1 200 $, CryptoBot ≈ 800 $ [допущение: ждёт подтверждения владельца].
6. **Цена решения «всё через юзербота».** У создания чека и у нажатия «Оплатить» нет ключа идемпотентности на стороне кошелька. Поэтому каждой операции заранее назначаем `random_id`: Telegram не создаёт второе сообщение с тем же `random_id`. Операции, которые выводят деньги, — одна попытка (CHECK в схеме). При неясном исходе — сверка (`find_issued_check`, статус счёта, баланс) или человек, но никогда не слепой повтор.
7. **Главные риски.** Заморозка аккаунтов кошельков вместе с резервами: AML у CryptoBot, ответа поддержки ждут неделями. Бан аккаунта Telegram за автоматизацию. Смена текстов ботов кошельков. Ввод PIN CryptoBot программой: справка CryptoBot это прямо запрещает. Неясный правовой статус обменника. Защита: минимальные резервы, ежедневный вывод прибыли, два выделенных аккаунта, при незнакомом ответе кошелька направление само встаёт на паузу.
8. **Технические решения.** Rust, один процесс на tokio. MTProto — `grammers` `=0.10.0`, только в крейте `mtproto`; остальной код знает лишь трейт `Transport`. Bot API — свой тонкий клиент `botapi` (Bot API 10.3: rich messages, цветные кнопки, `copy_text`). PostgreSQL 16 + `sqlx` 0.9, деньги только в `rust_decimal`, леджер с двойной записью. Transactional outbox, FSM заявки с охраной переходов в БД, актор на аккаунт юзербота (одно денежное действие в полёте), сверка с реальными балансами.
9. **Двойную выплату исключают три уровня.** (а) `random_id` операции: повтор отправки внутри попытки — только с ним. (б) Уникальные индексы БД: на заявку не больше одной расчётной операции, один чек — одна активация, один счёт — одна оплата. (в) Одна попытка для операций, выводящих деньги, и сверка вместо повтора.
10. **Принятый чек не теряется.** Операцию записываем в БД до отправки команды. Каждый ответ бота кошелька сохраняем в `wallet_messages` до разбора. После рестарта догоняем историю чата с кошельком.
11. **Интерфейс.** Главное меню reply-клавиатурой, инлайн-кнопки, одно сообщение на заявку, которое правится по шагам. Итог — «Ваш чек xRocket на 97.50 USDT» с кнопками «Забрать чек» и «Скопировать ссылку». Справочные экраны — rich messages с HTML-фолбэком. Логи владельцу — в отдельном ops-боте с темами.
12. **Деплой.** DigitalOcean AMS3: Docker Compose (приложение + PostgreSQL), ufw, бэкапы `pg_dump` с шифрованием `age`, healthchecks.io как «пульс». Пошагово — раздел 12.

## 1. Проверка платформ

### 1.1. Итоговая таблица «операция × способ»

Все операции делает **юзербот** — обычный аккаунт Telegram, которым программа управляет через MTProto (grammers). На каждую платформу — свой выделенный аккаунт; руками им не пользуются. Юзербот работает с **личным балансом** аккаунта, и этот баланс и есть кошелёк сервиса: `cb` (CryptoBot) и `xr` (xRocket). Платёжные API кошельков (для приложений-мерчантов) не используем совсем (Р2): ни токенов, ни баланса приложения, ни вебхуков.

Боты кошельков — только закреплённые по peer ID: CryptoBot `@send` (`1559501630`), xRocket `@xrocket` (`5014831088`) [проверено: lovec `claimer.rs:431`; при старте сверяются через resolve].

**Почему так и чем платим.**

- Владелец решил работать только через юзербота (Р2): один тип интеграции, никаких комиссий платформ за приём, никаких токенов приложений, которые можно украсть отдельно от аккаунта.
- Платим тем, что у создания чека и у нажатия «Оплатить» нет ключа идемпотентности на стороне кошелька. Таймаут после отправки значит: неизвестно, создан ли чек. Защита (§10.5): `random_id` назначается до первой отправки; операции, выводящие деньги, — одна попытка; неясный исход → `find_issued_check`, статус счёта или баланс → событие или `MANUAL_REVIEW`.
- Инлайн — основной путь, меню — запасной. Повтор `sendInlineBotResult` с тем же `random_id` не создаёт второе сообщение [проверено: Telegram, ошибка `RANDOM_ID_DUPLICATE`, lovec `tests/send_outcomes.rs`] и, по нашему допущению, второй чек [допущение M0: чек создаётся при отправке результата, а не при инлайн-запросе — HANDOVER §7, п. 3]. Если окажется, что чек создаётся уже на запросе, основным станет меню.
- Ссылка на чек выплаты не привязана к клиенту: забрать чек может любой, у кого есть ссылка. Отдаём её только в личку клиенту и прямо пишем «не пересылайте». Можно ли в меню кошельков привязать чек к пользователю — вопрос M0; если можно, делаем.

### 1.2. Ссылки на чеки и счета: форматы и распознавание

| Платформа | Бот (точное имя) | Чек | Счёт | Источник |
|---|---|---|---|---|
| CryptoBot | `send`, алиас `CryptoBot`; тестнет `CryptoTestnetBot` — не принимаем | `?start=CQ` + 10 символов (всего 12) | `?start=IV…` | чек и боты — [проверено: lovec `bots.rs:46-86`, `links.rs:141`, боевые логи]; `IV…` — [проверено: справка CryptoBot «How do I pay an invoice»] |
| xRocket | `xrocket`, алиас `tonRocketBot`; тестнет `xrocket_testnet_bot`, `ton_rocket_test_bot` — не принимаем | `t_` + 15 (17); мульти-чеки `mci_` + 15 (19), `mc_` + 15 (18) и `mc_` + 10 (13) активируются только в приложении xRocket → отказ (DESIGN-v0.2 Р8) | `?start=inv_…` | [проверено: lovec `bots.rs:65-86`, AUDIT-2.md:1776]; длина кода счёта не зафиксирована |

Распознавание (`parsers::links`):

1. **Источники ссылок в сообщении:** текст, сущности `url`/`text_link`, URL-кнопки `reply_markup` и голые коды чеков (`CQ…`, `t_…`; голый код мульти-чека xRocket — отказ с объяснением). Кнопки важны: клиенты пересылают сообщение-чек из @send, где ссылка лежит в кнопке, или создают инлайн-чек прямо в чате с нашим ботом (`@send 10usdt`). Голые коды счетов не принимаем: `IV…` легко спутать с обычным словом.
2. **Разбор — через `url::Url`, не регуляркой по всему тексту.** Допустимые формы (тесты открытого ловца [moukpu/cryptobot-link-catcher](https://github.com/moukpu/cryptobot-link-catcher/blob/main/tests/test_links.py) и lovec): `https://t.me/<bot>?start=<p>`, `t.me/<bot>?start=<p>`, `telegram.me`, `telegram.dog`, `www.`-префикс, `https://<bot>.t.me/?start=<p>`, `t.me/<bot>/app?startapp=<p>`, `tg://resolve?domain=<bot>&start=<p>` (и с `start` раньше `domain`), `tg:resolve?domain=@<bot>&start=<p>`, `?ref=…&start=<p>`.
3. **Валидация:** имя бота сравниваем без учёта регистра с белым списком из таблицы; `start` — по формату кода из таблицы; любые не-ASCII символы в имени бота (кириллические двойники «СryptoBot») → отказ «поддельная ссылка». Тестнет определяем по имени бота (известные имена или слово `testnet`), а не по всей ссылке: `t.me/send?ref=testnet_promo&start=…` — обычный чек [проверено: lovec AUDIT-2.md:375-388].
4. **Защита от фишинга:** юзербот **никогда не переходит по ссылке как по URL** и не резолвит имя из ссылки. Наружу уходит только код, и отправляется он боту по **закреплённому peer ID** (`mtproto::config`: CryptoBot `1559501630`, xRocket `5014831088`). При старте транспорт сверяет ботов через resolve; расхождение → CRITICAL и стоп. Переменные `CRYPTOBOT_PEER_ID`, `XROCKET_PEER_ID` — необязательная дополнительная сверка. Ответ засчитывается, только если пришёл от этого peer ID.
5. **Ложные срабатывания:** реферальные и сервисные параметры (`start=r-…`, `start=pay`, `startapp=…` без префикса счёта) → «Это не чек и не счёт». Несколько ссылок в одном сообщении → обрабатываем первую, о прочих говорим «по одной, пожалуйста».
6. **Сумма из ссылки не берётся никогда:** её там нет, а подпись к пересланному сообщению может быть подделана. Сумма — только из ответа бота кошелька нашему аккаунту.

### 1.3. Активация чека из обычного аккаунта: ответы ботов кошельков

**Как отправляем.** `messages.sendMessage` боту по закреплённому peer ID, текст `/start <код>`, `no_webpage`, заранее сохранённый `random_id` [проверено: lovec `fastsend.rs`, 167 доставленных команд]. Так же работают ссылки `startapp` (DESIGN-v0.2 §3). Хелпер `client.send_message` grammers не годится: он генерирует свой `random_id`, и безопасный повтор становится невозможен.

**Как ловим ответ.** Боты кошельков не ставят `reply_to` [проверено: lovec AUDIT-2-notes.md:61]. Подписываемся на поток сообщений **до** отправки. Ответ — первое финальное сообщение бота с id больше id нашей команды. Правки того же сообщения (`UpdateEditMessage`) переклассифицируют ответ, промежуточное «обработка» ждёт дальше. Таймаут — 30 с. На аккаунт в полёте ровно одна денежная команда, поэтому сопоставление идёт по порядку (FIFO).

**Язык.** Язык ответов зависит от языка аккаунта. Юзербот подключается с `lang_code = ru` (`mtproto::config`), словари содержат русские и английские формы.

Классификатор (`parsers::replies`) — словари lovec, подстрока в нижнем регистре [проверено: lovec `replies.rs:41-99`]. Тексты пока синтетические, настоящие — M0 (В3).

| Класс ответа | Признак | Событие и что видит клиент |
|---|---|---|
| Получено | «вы получили», «успешно получили», «you received», «you have received», «successfully received» + `<число> <АКТИВ>`, **без** «от @» | `CheckActivated`; сумма и актив — из ответа; сверка с балансом в ближайшей сверке |
| Уже активирован | «уже активирован», «уже получен», «already activated», «already been activated», «already claimed» | `CheckRejected` → `INTAKE_FAILED`: «деньги у того, кто открыл чек первым». **Ловушка:** если наш первый `/start` выиграл, а второй ушёл с **новым** `random_id`, бот тоже ответит «уже активирован» [проверено: lovec AUDIT.md:46]. Поэтому повтор — только с тем же `random_id`, а после неясного исхода — сверка, не отказ |
| Не найден | «не найден», «не существует», «недоступен», «not found», «does not exist» | `CheckRejected`: «чек не найден — я ничего не получил». На совсем свежий чек xRocket иногда отвечает так по ошибке: если чеку ≤ 3 с — один повтор [проверено: lovec `ledger.rs:19-20`] |
| Не для нас | «не можете активировать», «предназначен для другого», «not intended for you», «cannot activate» | `CheckRejected`: «чек привязан к другому аккаунту, деньги остались в чеке» |
| С паролем | «пароль», «password» (проверяется после «неверный пароль») | `CheckRejected`: «чек с паролем не принимаю — деньги остались в чеке» (Р3). Пароль не спрашиваем и боту не отправляем. CryptoBot после такого ответа ждёт пароль текстом; следующий `/start` начинает новый диалог [проверено: lovec `password.rs:294-304`; допущение M0: ожидание пароля не мешает следующей команде другого чека] |
| Подписка | «подпиш», «подписк», «subscribe», «join the» | `CheckRejected`: «чек требует подписки — такие не принимаю». На каналы не подписываемся никогда |
| Капча | «капч», «captcha», «символы, которые вы видите», «на картинке» | `CheckRejected`: «чек с капчей не принимаю» |
| Только для Premium | упоминание Premium [допущение M0: текст] | `CheckRejected`: «чек только для Telegram Premium» |
| Мульти-чек CryptoBot (`CQ…`, DESIGN-v0.2 Р8) | ответ о зачислении доли [допущение M0] | сумма — доля, зачисленная нам, из ответа, как у обычного чека. Ответ без понятной суммы — `Unknown` → ручной разбор (деньги уже у нас). Мульти-чеки xRocket до `/start` не доходят: парсер отказывает (E08) |
| Обработка | «получение», «обработ», «processing», «подождите», «please wait» | промежуточный ответ: ждём правку или новое сообщение до таймаута |
| «Ваш чек активировал @…» | «ваш чек» + «активировал» или «получил» | не ответ на команду: подтверждение, что клиент забрал наш чек выплаты (отчёт о незабранных чеках) |
| Входящий перевод | «Вы получили 5 USDT от @x» | не ответ на команду и не выигрыш, хотя совпадает со словарём «получено»: отличаем по «от @» и по отсутствию ожидающей команды [проверено: lovec AUDIT.md:82]; сохраняем для сверки |
| Ограничение аккаунта | «аккаунт ограничен», «обратитесь в поддержку» [допущение M0: текст] | `BotError::AccountRestricted`: CRITICAL, автопауза всех направлений этого кошелька, заявка — в сверку или `MANUAL_REVIEW` (П15) |
| FLOOD_WAIT | ошибка Telegram `FLOOD_WAIT_X` | пауза всего аккаунта на X с; операция не начиналась → назад в `pending`, попытка не тратится. Пороги из lovec: 29 с после 10 команд боту за 60 с; xRocket однажды дал 703 с, рестарт паузу не снимает [проверено: lovec AUDIT-2.md:1491, 1787-1791] |
| Нет ответа 30 с | — | `IntakeOutcomeUnknown` → `INTAKE_UNKNOWN` → сверка: догон истории чата и баланс |
| Незнакомый текст | ни один класс не подошёл или подошли два | `Unknown` → `INTAKE_UNKNOWN`, **автопауза направления**, CRITICAL с замаскированным сырым текстом (§10.6) |

Извлечение суммы: регулярное выражение по числу с разделителями `.`/`,`/тонкий пробел и кодом актива из словаря платформы (`USDT`, `TON`/`TONCOIN`, …). Результат — в `Decimal` без промежуточного `f64`. Защита от абсурда: сумма > 10 × `max_amount` → `MANUAL_REVIEW`.

### 1.4. Виды счетов

Платёжные API кошельков больше не источник фактов о счетах: юзербот видит только карточку счёта в чате с ботом. Всё ниже, кроме префиксов ссылок, — [допущение M0: снять карточки счетов обеих платформ, HANDOVER §7, п. 6].

| Признак | Счёт CryptoBot (`IV…`) | Счёт xRocket (`inv_…`) |
|---|---|---|
| Валюта | крипта или фиат (USD, EUR, RUB и другие); у фиатного счёта карточка показывает и сумму в выбранном активе | только крипта |
| Количество оплат | одна | бывают многоразовые и «любая сумма» — такие не принимаем |
| Статус на карточке | активен / оплачен / истёк. `parsers::replies::parse_invoice_card` ставит статус, только если в тексте ровно одно слово статуса без отрицания, иначе `Unknown` | то же |
| Оплата | кнопка валюты → «Оплатить» → мини-приложение → PIN | кнопка валюты → «Оплатить» |

Как получаем сумму, актив и статус **чужого** счёта: `inspect_invoice` — `/start IV…` или `/start inv_…` и разбор карточки. Открытие не оплачивает счёт [допущение M0]. Принимаем счёт, только если он одноразовый, с фиксированной суммой, оплачивается в USDT, активен и истекает не раньше чем через TTL котировки + 5 минут.

**Счёт в фиате.** Сумму в USDT берём у самого кошелька: из карточки счёта или с экрана после выбора USDT, не нажимая «Оплатить» [допущение M0]. Добавляем буфер `fiat_buffer_pct` = 1 % и фиксируем котировку на 15 минут (`domain::pricing::fiat_to_asset`). Перед нажатием «Оплатить» юзербот ещё раз читает сумму в USDT. Если она больше `A` из котировки — заявка уходит в возврат с объяснением «курс сдвинулся сильнее буфера», а не в доплату за свой счёт. Если кошелёк не показывает сумму в USDT до оплаты — фиатные счета не принимаем (E17).

### 1.5. Создание чека и оплата счёта из обычного аккаунта

| Способ | Как работает через MTProto | Что автоматизируется надёжно | Вердикт |
|---|---|---|---|
| Инлайн-режим `@send 97.5usdt` / `@xrocket 97.5` | `messages.getInlineBotResults` (peer — «Избранное») → результат с USDT и ровно этой суммой → `messages.sendInlineBotResult` в «Избранное» с заранее сохранённым `random_id` → ссылка из URL-кнопки отправленного сообщения. Кнопка может появиться не сразу, а правкой сообщения [проверено: lovec `ingest.rs:112-128`] | создание чека из личного баланса; повтор отправки тем же `random_id` не создаёт второе сообщение | **основной путь** выплаты и возврата (Р5) |
| Меню бота | CryptoBot: `/checks` → «Создать чек» → USDT → сумма → ссылка. xRocket: `/cheques` → «Персональный» → «Создать чек» → USDT → сумма → ссылка. Кнопки нажимаем через `messages.getBotCallbackAnswer` и ищем **по тексту**, не по позиции | работает, но у нажатий кнопок нет `random_id`: таймаут после ввода суммы значит «исход неизвестен» | **запасной путь**, только если инлайн не удался **до** отправки результата |
| Кнопки чужого счёта | `/start IV…` или `/start inv_…` → кнопка валюты → «Оплатить» (`messages.getBotCallbackAnswer`) | открыть счёт и выбрать валюту; у xRocket — и оплатить [допущение M0] | часть `pay_invoice` |
| Мини-приложение CryptoBot | кнопка «Оплатить» ведёт в мини-приложение → `messages.requestWebView` → URL с `tgWebAppData` → дальше HTTP самого мини-приложения и ввод PIN | MTProto заканчивается на URL. Дальше два варианта: повторить запросы мини-приложения по записи HAR (быстро, хрупко) или headless-браузер (тяжело) [LOVEC-PORTING §8.3] | решение владельца (Р4): PIN вводит программа. До записи HAR — `PayOutcome::NeedsHuman`, платит оператор |

Правила `issue_check` (DESIGN-v0.2 §4, HANDOVER M2.1):

- ошибка **до** `sendInlineBotResult` (нет нужного результата, транспорт недоступен) → меню;
- ошибка или таймаут **после** отправки → `IssueOutcome::Unknown`. Меню нельзя: чек мог создаться. Дальше — только `find_issued_check`;
- в меню любая неясность после ввода суммы → `Unknown`;
- «недостаточно средств» → `InsufficientFunds`: чек точно не создан, направление встаёт на автопаузу.

```
   xRocket → CryptoBot (чек на чек, 1,5 %) и оплата счёта CryptoBot деньгами из xRocket (3,0 %).

   [cb] ──вывод в сеть USDT-TON, ≈ 0,5 USDT──▶ депозитный адрес [xr]

```

Где теряются деньги:

- сетевые комиссии ребалансировки (0,04–0,1 % оборота);
- округление в пользу сервиса — это **доход** (≤ 0,01 USDT на заявку);
- заморозка аккаунта — **вся сумма** на заблокированном кошельке до разблокировки;

- ошибки и ручные компенсации.

Значения — сид таблицы `directions` в `schema.sql`; меняются в админке (П11).

| Чек xRocket → чек CryptoBot (`xr_to_cb_check`) | 1,5 % | 0,5 / 3,0 % | 0,10 USDT | Встречный поток: пополняет сторону xRocket, которую опустошает основной, — делаем дешевле |
| Оплата счёта CryptoBot деньгами из xRocket (`pay_cb_invoice`) | 3,0 % | 2,0 / 4,0 % | 0,20 USDT | Больше шагов и риска: счёт истекает, мини-приложение и PIN, пока платит оператор. Тоже пополняет `xr` |
| Оплата счёта xRocket деньгами из CryptoBot (`pay_xr_invoice`) | 2,0 % | 1,0 / 3,5 % | 0,20 USDT | Тратит `xr`, как основной поток |

Лимиты по умолчанию: 2–300 USDT на заявку, новый клиент — до 100. Все направления в сиде закрыты (`is_open = FALSE`): открывает владелец.

**Ценовой рычаг балансировки.** Для направления `d`, которое платит (выплатой или оплатой счёта) со стороны `S`, вычисляем `s = clamp(1 − available(S) / target(S), −1, 1)`. Тогда `fee_d = clamp(base_d + k · s, floor_d, cap_d)`, где `k = 0,75 п.п.` (`directions.skew_k_pct`); результат округляется вверх до 0,01 п.п. (`domain::pricing::Lever`). Чем меньше денег на стороне выплаты, тем дороже направление.

Пример: сторона xRocket на 40 % от целевого резерва (480 из 1 200, `s = +0,6`), сторона CryptoBot на 160 % (1 280 из 800, `s = −0,6`). Комиссия CryptoBot → xRocket = 2,5 + 0,45 = **2,95 %**, xRocket → CryptoBot = 1,5 − 0,45 = **1,05 %**. Цена пересчитывается раз в минуту и фиксируется в котировке заявки. Клиент всегда видит ту цену, по которой будет обмен.

**Формулы и округление** (`domain::pricing`, все в `Decimal`, шаг `step` из `platform_assets.payout_step`, USDT = 0,01):

- Обмен чека: `fee_raw = max(amount_in · fee%, min_fee)`; `payout = floor_step(amount_in − fee_raw)`; `fee = amount_in − payout`. Остаток округления уходит в комиссию. Пример: 33,33 USDT при 2,5 % → `fee_raw` = 0,83325 → выплата 32,49, комиссия 0,84.
- Оплата счёта: клиент присылает `X = max(ceil_step(A · (1 + fee%)), ceil_step(A + min_fee))`, где `A` — сумма счёта в USDT. Комиссия = `X − A`. Пример: счёт 10 USDT при 3 % → `X` = 10,30.
- Счёт в фиате: `A = ceil_step(fiat_amount · (1 + fiat_buffer%) / rate)`. Что останется от буфера после фактической оплаты — доход; если не хватило — возврат (§1.4).
- Чек выплаты меньше минимума чека платформы не создаётся [допущение M0: минимум, `platform_assets.min_check`]. Поэтому минимальная заявка — 2 USDT.

**Точка безубыточности:** `V* = (F + p·C) / (m − r)`, где `F` — постоянные затраты, `p·C` — ожидаемые потери от заморозок, `m` — средняя маржа, `r` — доля ребалансировки в обороте. Базовые параметры: `(45 + 40) / (0,022 − 0,0004) ≈ 3 935 $` в месяц, то есть ≈ 131 $ в день, или ≈ 5 обменов по 25 $.

**Чувствительность:**

- Заморозка при `p = 10 %` в месяц: базовая прибыль падает до 403 $.
- Разовая заморозка всех резервов (2 000 $) равна 3,5 месяца базовой прибыли. Это главный финансовый риск: он важнее комиссий, поэтому резервы держим минимальными (§3).
- Если создание чека окажется платным (вопрос M0), маржа падает на эту плату: 0,10 USDT за чек при среднем чеке 25 $ — это −0,4 п.п., базовая прибыль ≈ 443 $. Тогда поднимаем `min_fee` или базовую комиссию.

## 3. Ликвидность и резервы

### 3.1. Два кошелька и их роли

Кошелёк сервиса на платформе — личный баланс аккаунта юзербота (`wallet_accounts`, метки `cb` и `xr`; в леджере — `asset:cb:USDT`, `asset:xr:USDT`). Активный кошелёк на платформе ровно один (индекс `wallet_accounts_one_active`); запасной аккаунт (например, `cb-reserve`) заводится с `is_active = false` и включается при бане основного (П15).

| Кошелёк | Наполняется | Расходуется |
|---|---|---|
| `cb` — аккаунт юзербота CryptoBot | чеки клиентов CryptoBot: основной поток `cb_to_xr_check` и оплата счетов xRocket `pay_xr_invoice` | чеки выплаты встречного потока `xr_to_cb_check`; возвраты по чекам CryptoBot; оплата чужих счетов CryptoBot `pay_cb_invoice`; вывод излишка на сторону xRocket |
| `xr` — аккаунт юзербота xRocket | чеки клиентов xRocket: `xr_to_cb_check` и `pay_cb_invoice`; поступления ребалансировки | чеки выплаты основного потока `cb_to_xr_check`; возвраты по чекам xRocket; оплата чужих счетов xRocket `pay_xr_invoice` |

### 3.2. Определения

- **Баланс по леджеру** `L(w)` — сумма проводок по счёту кошелька `w` (`wallet_available.ledger_balance`).
- **Удержания** `H(w)` — сумма активных `holds` по `w`.
- **Доступно** `A(w) = L(w) − H(w)`.
- **Реальный баланс** `R(w)` — экран «Кошелёк» в боте кошелька, который читает юзербот (`WalletBot::balances`). Расхождение `R − L` вне операций «в полёте» — сигнал сверки (§4, П14).
- **Перекос** `skew = (A(xr)/T(xr) − A(cb)/T(cb)) / (A(xr)/T(xr) + A(cb)/T(cb))`, где `T` — целевые резервы. Диапазон −1…+1; > 0 — деньги копятся на стороне xRocket, < 0 — на стороне CryptoBot (обычное состояние при основном потоке).

### 3.3. Сколько держать

Формула для каждой стороны выплаты:

`T(S) = 1,2 · max(k_peak · out_hour(S) · T_rebal, 2 · max_order)` плюс запас на оплату счетов этой платформы, где:

- `k_peak` = 4 — пиковый час к среднему [допущение: уточнить по статистике первого месяца];
- `T_rebal` = 6 ч — время ребалансировки с учётом сна владельца;
- `max_order` = 300 USDT.

Все значения таблицы — [допущение: ждёт подтверждения владельца, HANDOVER §7, п. 8].

| Кошелёк | Расчёт (базовый сценарий) | target | low (WARN, цена ↑) | critical (автопауза) | high (излишек) |
|---|---|---|---|---|---|
| `xr` | выплаты основного потока 700 $/день → 29 $/ч × 4 × 6 = 700 → ×1,2 = 840; запас на оплату счетов xRocket ≈ 360 | **1 200** | 600 | 150 | 2 000 |
| `cb` | выплаты встречного потока 300 $/день → 2 × 300 = 600 → ×1,2 = 720; запас на оплату счетов CryptoBot ≈ 80 | **800** | 400 | 150 | 1 400 |
| **Итого** | | **2 000** | | | |

Пессимистичный сценарий — 1 000 $ (`max_order` = 150). Оптимистичный — 8 000 $ (`max_order` = 500, `T_rebal` = 3 ч с дежурным оператором). Значения хранятся в `reserve_thresholds` и меняются в админке.

### 3.4. Правило «не принимаем, если не можем выплатить»

1. Перед активацией чека сумма неизвестна, а кошелёк зачисляет чек сразу на `/start` [проверено: lovec — ответ «вы получили» приходит на первую команду]. Поэтому удерживаем `hold = max_order_eff` на кошельке выплаты, где `max_order_eff = min(max_amount, A(payout) − 20 USDT)` (`domain::pricing::max_order_effective`).
2. Если `max_order_eff < min_amount`, чек **не активируем**: «Сейчас могу принять не больше N USDT, попробуйте через 10–15 минут». Деньги клиента не тронуты.
3. Удержание создаётся в той же транзакции, что и заявка, под `pg_advisory_xact_lock(wallet_account_id)`. Два одновременных чека не могут вдвоём занять один и тот же резерв.
4. После активации удержание уменьшается до точной суммы выплаты. Если сумма чека больше `max_order_eff` или актив не поддержан — возврат (§4, П8), а не частичная выплата.
5. Для оплаты счёта сумма известна заранее: удерживаем ровно `A` на кошельке платформы счёта (`cb` для счёта CryptoBot, `xr` для счёта xRocket).
6. `max_order_eff` показываем в «Курсе и лимитах» и в ответе на ссылку. Клиент видит лимит до отправки.

### 3.5. Перекос и ребалансировка

**Ловим перекос.**

- Монитор пересчитывает `A(w)` и `skew` раз в минуту.
- `|skew| > 0,5` дольше 30 минут → WARN в тему «Резервы».
- `A < low` → ценовой рычаг уже работает (§2.3), а владелец получает инструкцию.

**Порядок пополнения стороны выплаты (дешевле → дороже):**

1. **Встречный поток.** Рычаг (§2.3) удешевляет направления, которые пополняют истощённую сторону: при нехватке `xr` дешевеют `xr_to_cb_check` и `pay_cb_invoice`. Это бесплатно и работает само.
2. **Вывод в сеть между платформами.** Излишек `cb` → депозитный адрес USDT-TON аккаунта `xr` (обратное направление — так же). Адрес — только из белого списка (`settings.rebalance_whitelist`), добавление — только владельцем с двойным подтверждением. В MVP вывод делает владелец руками в сессии служебного аккаунта (Telegram Desktop), пока юзербот этого аккаунта на паузе (кнопка в `/ub`): ручные действия во время работы юзербота засоряют чат и ломают сопоставление ответов [проверено: lovec AUDIT-2.md:1498]. У CryptoBot для вывода нужен PIN. Бот ведёт заявку `rebalances` и ловит поступление сверкой. Вывод юзерботом (операция `withdrawal`, одна попытка) — позже (M8). [допущение: способ ребалансировки ждёт решения владельца]
3. **Через владельца.** Владелец забирает излишек одной стороны чеком, который юзербот создаёт по команде из ops-бота, и пополняет другую сторону своим чеком, который юзербот активирует как взнос капитала (`capital_in`). PIN для этого не нужен, но нужны деньги владельца на второй платформе.
4. **Размер пачки:** `ceil_50(target − A)`, не меньше 100 USDT, чтобы сетевая комиссия была < 0,5 % пачки.
5. **Проводки:** `Дт asset:transit / Кт asset:cb` при отправке; `Дт asset:xr / Кт asset:transit` при поступлении; `Дт expense:network_fee / Кт asset:cb` на комиссию.

**Автозакрытие направления** (`directions.auto_paused = true`, клиенты видят «временно на паузе»):

| Условие | Снятие |
|---|---|
| `A(payout) < min_amount + 20` | автоматически, когда условие держится 5 минут |
| Аккаунт юзербота в `flood_wait` > 5 мин или `logged_out`/`banned` | автоматически после восстановления и успешной сверки |
| Бот кошелька ответил «недостаточно средств» при создании чека или оплате | автоматически после сверки, если `A(payout)` снова выше порога |
| Незнакомый ответ кошелька (§10.6) | **только вручную** после обновления парсера |
| Расхождение сверки > 1 USDT | **только вручную** |
| Признак заморозки аккаунта кошелька | **только вручную** (§4, П15) |
| `kill_switch_payouts` | **только владелец** |

**Вывод прибыли.** Ежедневно в 03:10 UTC бот считает излишек выше `high` по каждому кошельку и предлагает владельцу «вывести N USDT». По подтверждению юзербот создаёт чек на эту сумму, владелец забирает его своим личным аккаунтом. Деньги вне сервиса не замораживаются вместе с его аккаунтами. [допущение: отдельного вида операции для такого чека в схеме пока нет — добавить в M8]

## 4. Бизнес-процессы

Общие правила для всех процессов:

- **Переходы.** Заявка меняет состояние только через `domain::fsm::transition`. Каждый переход записываем в `order_transitions`. Разрешённые переходы — `ALLOWED` в коде (31) = таблица `order_state_transitions` в БД; её охраняет триггер.
- **Деньги.** Каждое денежное действие — сначала строка в `operations` (outbox) в той же транзакции, что и переход. Действие юзербота — только после коммита `status = 'dispatched'`. Транзакция БД не держится во время действия юзербота.
- **Кто делает.** Все операции outbox выполняет юзербот (`operations.via = 'userbot'`; `manual` — если сделал оператор). Каждой операции заранее назначается `random_id` (хранится в `operations.request`). Операции, которые выводят деньги (`create_payout_check`, `create_refund_check`, `create_excess_check`, `pay_invoice`, `withdrawal`), — `max_attempts = 1` (CHECK в схеме). Повторять можно только `activate_check`, `open_invoice` и `read_balance`.
- **Клиент.** Видит одно сообщение прогресса, которое редактируется (§6).

Соответствие результатов юзербота событиям FSM (HANDOVER M3.3):

| Результат `WalletBot` | Событие |
|---|---|
| `ActivationOutcome::Received(m)` | `CheckActivated { fully_funded }` — сумма из ответа, а не из ссылки |
| `ActivationOutcome::Rejected(_)` | `CheckRejected` |
| `ActivationOutcome::Unknown` | `IntakeOutcomeUnknown` |
| `IssueOutcome::Issued` | `PayoutConfirmed` / `RefundConfirmed`, ссылка → `orders.payout_check_url` |
| `IssueOutcome::InsufficientFunds` | `PayoutFailed` / `RefundFailed` + автопауза направления |
| `IssueOutcome::Unknown` | сверка `find_issued_check` → Confirmed или Failed |
| `PayOutcome::Paid`, `AlreadyPaid` | `InvoicePaid` (`AlreadyPaid` — только если сверка подтверждает, что платили мы) |
| `PayOutcome::Expired` | `InvoiceUnpayable` |
| `PayOutcome::NeedsHuman`, `PayOutcome::Unknown` | `InvoicePayNeedsHuman` |
| `BotError::FloodWait`, `BotError::Unavailable` | операция не начиналась: назад в `pending` с `next_attempt_at`, попытка не тратится |

### П1. Обмен чека CryptoBot → xRocket (основной поток)

| | |
|---|---|
| Триггер | Клиент прислал ссылку `t.me/send?start=CQ…`: текстом, пересылкой сообщения-чека или инлайн-чеком `@send 100usdt` прямо в чате бота |
| Шаги | 1) разбор ссылки (§1.2); 2) проверки: бан, частота (5 заявок за 10 мин), дневной лимит, направление открыто, `max_order_eff(xr) ≥ min_amount`; 3) TX: `NEW → INTAKE_PENDING` (`LinkAccepted`), `hold(xr, max_order_eff)`, `operation(activate_check, intake, ord-<id>-intake-1, random_id)`; 4) воркер: `dispatched` (коммит) → юзербот CryptoBot шлёт `/start CQ…` и ждёт ответ (FIFO, 30 с); каждое сообщение бота — в `wallet_messages` до разбора; 5) «вы получили 100 USDT» → TX: `CheckActivated` → `RECEIVED`, проводка `intake` (Дт `asset:cb` / Кт `liability:payable`), котировка: выплата = 100 − 2,5 % = 97,50; 6) TX: `Settle(Payout)` → `PAYOUT_PENDING`, hold сжат до 97,50, `operation(create_payout_check, settle, ord-<id>-payout, random_id, max_attempts = 1)`; 7) воркер: юзербот xRocket — `inline_query("97.5")` у @xrocket → результат USDT → `send_inline` в «Избранное» с сохранённым `random_id` → ссылка `t.me/xrocket?start=t_…` из кнопки; не вышло **до** отправки — меню `/cheques`; 8) `Issued` → TX: `PayoutConfirmed` → `COMPLETED`, проводка `payout` (Дт payable 100 / Кт `asset:xr` 97,50 / Кт `revenue:fee` 2,50), hold → consumed, ссылка в `orders.payout_check_url`; 9) клиенту — «Ваш чек xRocket на 97.50 USDT» с кнопками «Забрать чек» и «Скопировать ссылку», лог в тему «Обмены» |
| Состояния | `NEW → INTAKE_PENDING → RECEIVED → PAYOUT_PENDING → COMPLETED` |
| Что ломается | уже активирован, не найден, не для нас, пароль, капча, подписка, Premium → `CheckRejected` → `INTAKE_FAILED`, hold снят, деньги клиента остались в чеке; нет ответа или незнакомый текст → `INTAKE_UNKNOWN` → сверка (история чата, баланс) → `RECEIVED` / `INTAKE_FAILED` / `MANUAL_REVIEW`; сумма вне лимитов или актив не USDT → возврат (П8); ошибка или таймаут **после** отправки инлайн-результата → `IssueOutcome::Unknown` → `find_issued_check` по `random_id`, сумме и времени: нашли — `PayoutConfirmed`, не нашли или неясно — `PayoutFailed` → `MANUAL_REVIEW`; «недостаточно средств» → `PayoutFailed` и автопауза направления. Повторно чек автоматически не создаём никогда |

### П2. Обмен чека xRocket → CryptoBot (встречный поток)

Симметричен П1, со своими отличиями:

- вход — `/start t_…` юзерботом xRocket, удержание на `cb`; мульти-чеки xRocket (`mci_…`, `mc_…`) не принимаем — они активируются только в приложении xRocket (DESIGN-v0.2 Р8);
- выплата — инлайн `@send 97.5usdt` юзерботом CryptoBot, ссылка `t.me/send?start=CQ…`; запасной путь — `/checks` → «Создать чек» → USDT → сумма;
- на совсем свежий чек xRocket иногда отвечает «не найден»: один повтор, если чеку ≤ 3 с (§1.3);
- мульти-чек CryptoBot (тот же `CQ…`, П1) — как обычный чек: сумма — наша доля из ответа бота. Ту же ссылку второй раз (другой клиент из того же канала) не открываем: наша доля уже получена — отказ `check_used`.

### П3. Оплата счёта CryptoBot деньгами из xRocket (`pay_cb_invoice`)

| | |
|---|---|
| Триггер | Ссылка `t.me/send?start=IV…` или `startapp`-ссылка со счётом |
| Шаги | 1) юзербот CryptoBot открывает счёт без оплаты (`inspect_invoice`, операция `open_invoice`): сумма, актив или фиат, статус, одноразовость; 2) проверки (§1.4) и резерв `A(cb) ≥ A`; 3) TX: `LinkAccepted` → `AWAITING_FUNDS`, котировка `X` с TTL 15 мин (`settings.quote_ttl_seconds`), `hold(cb, A)`; 4) клиент присылает чек xRocket на `X` → `ClientCheckSubmitted` → `INTAKE_PENDING`, `activate_check` (как в П2, заявка та же); 5) пришло `≥ X` → `RECEIVED` (недоплата — П6); 6) TX: `Settle(PayInvoice)` → `INVOICE_PAY_PENDING`, `operation(pay_invoice, settle, ord-<id>-pay, max_attempts = 1)`; 7) юзербот снова открывает счёт: всё ещё активен? → кнопка USDT → «Оплатить» → кнопка мини-приложения → `open_webapp` → PIN; 8) «Счёт оплачен» → `InvoicePaid` → `COMPLETED`, проводка `invoice_paid` (Дт payable X / Кт `asset:cb` A / Кт `revenue:fee` X − A), hold → consumed; 9) клиенту — «Счёт оплачен», продавец видит оплату у себя |
| Пока нет записи HAR | Шаг 7 заканчивается `PayOutcome::NeedsHuman` → `InvoicePayNeedsHuman` → `MANUAL_REVIEW`. Оператор получает в ops-боте задачу «оплати счёт вручную» и платит со служебного аккаунта CryptoBot в Telegram Desktop, пока юзербот этого аккаунта на паузе [допущение: порядок ждёт решения владельца]. Затем нажимает «Оплачено» (`Operator(CloseAsPaid)`, с доказательством) или «Не получилось» (`Operator(Refund)`). SLA — 15 минут в рабочее время, клиент видит экран S8 |
| Что ломается | счёт оплачен или истёк до шага 7 → `InvoiceUnpayable` → `REFUND_PENDING` (П8); таймаут или незнакомый ответ после «Оплатить» → `PayOutcome::Unknown` → `MANUAL_REVIEW`. **Повторно не нажимаем.** Открываем счёт ещё раз: оплачен и баланс `cb` уменьшился на `A` → оператор закрывает «оплачено»; оплачен, а баланс не уменьшился — счёт оплатил кто-то другой → возврат |

### П4. Оплата счёта xRocket деньгами из CryptoBot (`pay_xr_invoice`)

Симметричен П3:

- открытие `inv_…` юзерботом xRocket, удержание на `xr`, клиент присылает чек CryptoBot;
- оплата — кнопками в чате xRocket, без мини-приложения [допущение M0: поток не записан];
- многоразовые счета и счета «любая сумма» отклоняем на шаге проверок: при неясном исходе повторная оплата такого счёта — реальная двойная оплата.

### П5. Счёт в фиате

| | |
|---|---|
| Триггер | При открытии счёта П3 выяснилось, что он в фиате |
| Шаги | сумма в USDT — из карточки кошелька (§1.4) → `A = ceil_step(fiat · 1,01 / rate)` (`domain::pricing::fiat_to_asset`) → котировка `X` по §2.3; перед оплатой юзербот снова читает сумму в USDT: `≤ A` → платим; `> A` → `REFUND_PENDING` с текстом «курс сдвинулся больше чем на 1 %, верну деньги чеком, пришлите ссылку ещё раз» |
| Что ломается | кошелёк не показывает сумму в USDT до оплаты → счёт не принимаем (E17); USDT нельзя выбрать → отказ до приёма денег |

### П6. Недоплата и переплата

| Ситуация | Реакция |
|---|---|
| Пришло меньше `X` (оплата счёта) | `CheckActivated { fully_funded: false }` → назад в `AWAITING_FUNDS` (переход `INTAKE_PENDING → AWAITING_FUNDS`), `intake_amount` накапливается, клиенту — «Пришло 7,00 из 10,30. Дошлите чек на 3,30 до HH:MM — или верну то, что пришло». По истечении TTL → `QuoteExpired { funds_received: true }` → `REFUND_PENDING` на всю полученную сумму (за недоплату комиссию не берём) |
| Пришло больше `X` | Оплачиваем счёт. Излишек ≥ `min_refund_amount` (0,50 USDT) → `operation(create_excess_check, excess_refund, ord-<id>-excess)` — чек на излишек на платформе входа; меньше — проводка `excess_kept` в доход, и прямо пишем об этом в итоге |
| Чек больше `max_order_eff` (обмен) | Полный возврат (П8): частичная выплата сложнее объяснить и сверить |

### П7. Истёкший или уже оплаченный счёт

| Момент | Реакция |
|---|---|
| При открытии (до денег) | Отказ: «Не могу оплатить этот счёт: он уже оплачен / истёк. Деньги не списаны. Попросите у продавца новый счёт» |
| Истёк, пока ждали деньги клиента | Денег ещё нет → `EXPIRED`; часть пришла → `REFUND_PENDING` |
| Оплачен кем-то другим между нашим открытием и нажатием | `InvoiceUnpayable` → `REFUND_PENDING`, клиенту — «Счёт успели оплатить до меня. Верну ваши X чеком» |
| Повторная ссылка на счёт, который мы уже оплатили | Индекс `orders_invoice_param_completed` не даст создать заявку: «Этот счёт уже оплачен, заявка №…» |

### П8. Возврат

| | |
|---|---|
| Триггер | Сверх лимита; неподдерживаемый актив; счёт стал неоплачиваемым; истёк TTL при частичной оплате; отмена клиентом после частичной оплаты; решение оператора |
| Шаги | TX: `REFUND_PENDING`, hold снят, `operation(create_refund_check, settle, ord-<id>-refund, random_id, max_attempts = 1)` на платформе **входа** (деньги возвращаются туда, откуда пришли), сумма = `intake_amount` (комиссию за несостоявшийся обмен не берём) → юзербот создаёт чек, как в П1, шаг 7 → `RefundConfirmed` → `REFUNDED`, проводка `refund` (Дт payable / Кт кошелёк входа); клиенту — «Возврат готов: ваш чек CryptoBot на …» с кнопкой «Забрать чек» |
| Инварианты | Возврат невозможен, пока есть живая или успешная выплата (`operations_one_settle_per_order`). Из `PAYOUT_PENDING` в возврат — только через ручной разбор. Неподдерживаемый актив (например, TON до v1.0) возвращаем чеком в том же активе — он только что пришёл на кошелёк |
| Что ломается | неясный исход создания чека → `find_issued_check` → `RefundConfirmed` или `RefundFailed` → `MANUAL_REVIEW` |

### П9. Ручной разбор

| | |
|---|---|
| Триггер | `MANUAL_REVIEW` из любого шага: неясный исход создания чека или оплаты, неоднозначная сверка приёма, незнакомый ответ, оплата счёта CryptoBot до записи HAR, стоп-кран |
| Шаги | 1) алерт в «Ошибки» с карточкой заявки, сырыми ответами кошелька и кнопками; 2) оператор смотрит факты: ответы бота, «Избранное» и список чеков служебного аккаунта, баланс, статус счёта; 3) решение (событие `Operator(...)`): «Повторить выплату» (`RetryPayout`: новая операция `ord-<id>-payout-2` с новым `random_id` — **только** после того, как оператор убедился, что прежняя попытка чек не создала, и пометил её `failed`), «Повторить оплату» (`RetryInvoicePayment` — после проверки статуса счёта), «Вернуть» (`Refund`), «Закрыть: выплачено» (`CloseAsPaid` — обязательно доказательство: ссылка на созданный чек или скриншот оплаты), «Закрыть без выплаты» (`CloseWithoutPayout` — только владелец, с причиной); 4) запись в `admin_audit`, клиенту — понятный итог |
| SLA | Ответ клиенту ≤ 15 мин в рабочее время; заявка в разборе > 30 мин → повторный CRITICAL |
| Ограничения | Ручная выплата > `staff.max_manual_payout` (оператор — 50 USDT, админ — 300 USDT) требует подтверждения владельца |

### П10. Ребалансировка — §3.5, диаграмма [`04-activity-rebalance`](diagrams/04-activity-rebalance.puml)

| | |
|---|---|
| Состояния `rebalances` | `planned → confirmed → sent → arrived → completed` (или `failed` / `cancelled`) |
| Что ломается | Вывод не прошёл → `failed`, деньги остаются на кошельке (сверка подтвердит); поступление не пришло за 2 ч → CRITICAL, проверка хеша транзакции в обозревателе сети; адрес не из белого списка → отказ на уровне кода |

### П11. Смена маржи и лимитов

Кто: админ или владелец. Шаги: команда → предпросмотр «было/станет», пример расчёта на 25 и 100 USDT → подтверждение → `directions` + `admin_audit`.

- Котировки, уже выданные клиентам, не меняются: цена фиксируется в заявке.
- Изменение > 1 п.п. за раз требует подтверждения владельца.

### П12. Бан и разбан

Кто: админ. Обязательны причина (≥ 3 символов) и срок (1 д / 7 д / 30 д / бессрочно).

- Активные заявки банимого **не обрываются**: доводим до выплаты или возврата. Деньги клиента не конфискуются без решения владельца и причины.
- Клиент видит: «Доступ ограничен до DD.MM. Причина: … Вопросы — /help».
- Разбан — с причиной. Всё пишется в `admin_audit`.

### П13. Пауза направления и режим обслуживания

| Действие | Что видит клиент | Заявки в работе |
|---|---|---|
| Пауза направления | «Направление временно на паузе» до активации чека | доводятся |
| Режим обслуживания | Новые ссылки не принимаются, баннер с причиной и ориентиром по времени | доводятся |
| `kill_switch_payouts` (включить — любой сотрудник, выключить — только владелец) | «Кошелёк отвечает с задержкой, ваши деньги зарезервированы» | операции, выводящие деньги, не отправляются: остаются в `pending`, попытка не тратится; при выключении — продолжаются с теми же `random_id` |

### П14. Сверка балансов — диаграмма [`05-activity-recovery-reconcile`](diagrams/05-activity-recovery-reconcile.puml)

| | |
|---|---|
| Частота | По каждому кошельку раз в 15 мин и после каждых 10 заявок: юзербот читает экран «Кошелёк» (`balances`) |
| Формула | `expected = L(w)`; если по кошельку есть операции `dispatched`/`unknown`, замер помечается `skipped_inflight` и повторяется через 30 с |
| Допуск | `settings.reconcile_tolerance`: `|R − L| ≤ 0,01` → ok; ≤ 1 USDT → WARN; > 1 USDT → пауза направлений этого кошелька и CRITICAL |
| Разбор расхождения | `R > L` — пришли деньги без заявки (входящий перевод? чек мимо бота? ребалансировка не учтена?) → проводка `adjustment` только руками владельца с причиной; `R < L` — **неучтённое списание** (утечка сессии? лишний чек? ручное действие в аккаунте?) → «Безопасность» CRITICAL + стоп выплат с этого кошелька |

### П15. «Аккаунт кошелька заморожен»

| | |
|---|---|
| Сигналы | Ответ бота кошелька об ограничении (`BotError::AccountRestricted`); ошибки авторизации Telegram (`AUTH_KEY_UNREGISTERED`, `USER_DEACTIVATED`); сверка: баланс меньше леджера; сообщения поддержки кошелька |
| Реакция | Автопауза всех направлений, где участвует кошелёк. Заявки в полёте: деньги клиентов ещё не приняты — отказ; приняты — выплата с запасного аккаунта этой платформы (если он есть и в нём есть резерв) или `MANUAL_REVIEW` с честным текстом клиенту. CRITICAL владельцу с чек-листом |
| Чек-лист владельца | 1) не создавать новые аккаунты с тех же устройств и IP; 2) написать в поддержку кошелька с фактами (оборот, правила сервиса, что это обменник); 3) зафиксировать сумму под заморозкой как `expense:loss` (провизия) до разблокировки; 4) решить, включать ли запасной аккаунт (`wallet_accounts.is_active`) |

### П16. Восстановление после падения

| Шаг | Действие |
|---|---|
| 1 | Старт в режиме «прогрев»: новые заявки не принимаются |
| 2 | Юзерботы подключаются и догоняют историю чатов с ботами кошельков и «Избранного» с курсора `wallet_chat_cursors.last_message_id` (`messages.getHistory`); сырые сообщения сохраняются |
| 3 | Операции в полёте — по правилам ниже |
| 4 | Сверка всех кошельков |
| 5 | Нет расхождений → приём открывается, INFO «Перезапуск, восстановлено N заявок» |

| Операция в статусе | Правило |
|---|---|
| любая `pending` | выполняется как обычно: действие ещё не начиналось |
| `activate_check` `dispatched` | Ищем ответ среди сохранённых и догнанных сообщений; нет — повторяем `/start` **с тем же `random_id`**: Telegram вернёт прежнее сообщение или `RANDOM_ID_DUPLICATE` |
| `create_payout_check`, `create_refund_check`, `create_excess_check` `dispatched` | **Не повторяем.** `find_issued_check` в «Избранном» и в списке чеков бота → Confirmed или Failed; при неясности — `MANUAL_REVIEW` |
| `pay_invoice` `dispatched` | **Не повторяем.** Читаем статус счёта и баланс, при неясности — `MANUAL_REVIEW` |

### П17. Чек с паролем

Чек с паролем отклоняем как любой неподходящий чек (Р3): `CheckRejected` → `INTAKE_FAILED`, клиенту — «Чек с паролем не принимаю — деньги остались в чеке. Создайте чек без пароля и пришлите его сюда». Пароль у клиента не спрашиваем, боту не отправляем, нигде не храним. В оплате счёта отказ по чеку возвращает заявку в `AWAITING_FUNDS`: клиент может прислать другой чек.

### П18. Вывод прибыли

Раз в сутки — предложение владельцу (§3.5). Проводка `profit_sweep: Дт equity:owner_withdrawals / Кт кошелёк` — после того, как чек на владельца создан и сверка подтвердила списание.

### П19. Отмена клиентом

Кнопка «Отмена» есть только в `AWAITING_FUNDS` (`ClientCancelled`). Денег ещё нет → `CANCELLED`. Если часть уже пришла (недоплата), отмена превращается в возврат (П8): кнопка «Вернуть деньги».

### 4.20. Порядок шагов, при котором падение не ведёт к двойной выплате или потере денег

Сценарий обмена чека; «падение» — `kill -9` процесса, обрыв сети или рестарт сервера.

| # | Шаг | Падение сразу после шага | Что будет после рестарта | Почему безопасно |
|---|---|---|---|---|
| 1 | TX: заявка `INTAKE_PENDING` + hold + `operation(activate_check, pending, random_id)` | Чек не отправлен кошельку | Воркер берёт `pending` и отправляет | Деньги не тронуты |
| 2 | TX: `operation → dispatched`, `attempts + 1` (**коммит до отправки**) | Неизвестно, ушла ли команда | Догоняем историю чата; ответа нет — повторяем `/start` с **тем же** `random_id` | Telegram не создаст второе сообщение (`RANDOM_ID_DUPLICATE`); второй раз кошелёк чек не зачислит |
| 3 | Юзербот отправил `/start`, кошелёк зачислил | Ответ мог не сохраниться | Догон истории (`getHistory` с курсора) → ответ «вы получили X» найден и разобран | Ответы бота хранятся в Telegram, мы их перечитываем |
| 4 | `wallet_messages` сохранён | — | Повторная обработка того же ответа не задвоит проводку: `ledger_tx_once_per_operation` | Идемпотентность по `operation_id` |
| 5 | TX: `RECEIVED` + проводка `intake` | — | `RECEIVED` без расчётной операции → движок заново решает: выплата или возврат | Решение детерминировано по данным заявки |
| 6 | TX: `PAYOUT_PENDING` + `operation(create_payout_check, pending, random_id, max_attempts = 1)` | Чек не создан | Воркер отправляет как обычно | Вторую расчётную операцию не даст `operations_one_settle_per_order` |
| 7 | TX: `operation → dispatched` (коммит), затем инлайн-запрос и отправка результата в «Избранное» | Неизвестно, создан ли чек | **Не повторяем.** `find_issued_check`: сообщение в «Избранном» с нашей суммой после начала операции, список чеков бота → `PayoutConfirmed` или `MANUAL_REVIEW` | Одна попытка (CHECK `max_attempts = 1`); сверка вместо повтора |
| 8 | Ссылка на чек получена | Не записана в БД | Как шаг 7: сверка найдёт сообщение-чек в «Избранном» | Сообщение хранится в Telegram |
| 9 | TX: `COMPLETED` + проводка `payout` + hold consumed + `payout_check_url` | — | Терминальное состояние, ничего не делаем | Триггер не пустит из `COMPLETED` никуда |
| 10 | Правка сообщения клиенту | Клиент не увидел итог | Отложенная задача «уведомить» по `progress_message_id` — повторяемая, без денег | — |

Внутри одной попытки повтор отправки возможен, но только с тем же `random_id`: например, соединение оборвалось до ответа сервера. Для `sendInlineBotResult` это значит, что повтор не создаст второе сообщение и, по допущению, второй чек [допущение M0]. В меню бота у нажатий кнопок `random_id` нет, поэтому после ввода суммы любая неясность — сразу `Unknown`. Оплата счёта устроена так же: одна попытка, после неясного исхода — только сверка или ручной разбор (П3).

## 6. Интерфейс клиента

Все тексты — в [`crates/ui/ru.toml`](crates/ui/ru.toml), экраны — в `crates/ui/src/screens/`, снимки всех экранов — `crates/ui/tests/snapshots/` (41 снимок `insta`). Ниже — что на каком экране и почему; дословный текст — в `ru.toml`.

### 6.1. Принципы и технические решения

- **Главное меню** — reply-клавиатура (`is_persistent`, `resize_keyboard`, подсказка в поле ввода «Пришлите чек или ссылку на счёт»):
  - `💱 Обменять чек` · `🧾 Оплатить счёт`
  - `📈 Курс и лимиты` · `📜 История`
  - `💬 Поддержка`

  При Premium у владельца — иконка `icon_custom_emoji_id` вместо эмодзи в тексте кнопки и `style: primary` у двух главных действий.
- **Главный сценарий без меню.** Чек или ссылка на счёт в любой момент запускает заявку. Меню нужно, чтобы объяснить, что прислать. Команды: `/start`, `/terms` (курс и лимиты), `/history`, `/help`, `/privacy`.
- **Одно сообщение на заявку.** Создаём его при получении ссылки и затем только **редактируем** (`editMessageText`) по шагам: не чаще 1 раза в секунду на чат, промежуточные шаги можно сливать. Новое сообщение отправляем только для итога, если с момента создания прошло больше 60 с: так клиент получит уведомление.
- **Rich messages — только для справочных экранов** (приветствие, курс и лимиты, история, карточка заявки, помощь, админские сводки). Денежный поток (прогресс, котировки, итоги, ошибки) — **обычные HTML-сообщения**, их показывает любой клиент. Обоснование:
  - в Telegram Web и старых клиентах на месте rich-сообщения бывает заглушка «не поддерживается» [факт основателя, пример opencrabs];
  - заглушка вместо «пришлите чек на X» недопустима.
  Отвергнутая альтернатива — rich везде и надежда, что клиент обновится.
- **Фолбэк.** Каждый справочный экран собирается сразу в двух видах — rich-HTML и обычный HTML (`ui::doc::Doc`, по образцу lovec `format.rs`). Rich отправляется через `sendRichMessage` (`rich_message: {html, skip_entity_detection: true}`) клиентом `botapi`. Под rich-экраном — кнопка «Не отображается?»: она переключает клиента на простой вид и сразу присылает HTML-версию. Ниже rich-экраны для наглядности показаны в HTML-нотации (`<h3>`, `<table>`, `<details>`, `<footer>`) [проверено: соответствие блоков тегам в спецификации Bot API 10.3].
- **Разметка обычных сообщений:** `<b>`, `<i>`, `<u>`, `<s>`, `<tg-spoiler>`, `<code>`, `<pre>`, `<blockquote>`, `<blockquote expandable>`, `<a href>`, `<tg-emoji emoji-id>`, `<tg-time unix format>` [проверено: парсер HTML в TDLib `MessageEntity.cpp`]. Все подстановки экранируются (`&`, `<`, `>`); тест `ui/tests/html_valid.rs` проверяет каждый экран. Строки формата `tg-time` (`t`, `dt`) — [допущение: сверить с разделом «date-time entity formatting» Bot API; текст внутри тега — запасной для старых клиентов].
- **Суммы, ссылки, номера заявок — моноширинным.** Рядом кнопка `copy_text` (1–256 символов [проверено]).
- **Кнопки** [проверено: `InlineKeyboardButton.style`, `icon_custom_emoji_id`, `disabled`]:
  - основное действие — `style: "primary"` (синяя) или `"success"` (зелёная, например «Забрать чек»);
  - отмена — без `style` (нейтральная);
  - опасное действие — `"danger"` (красная);
  - недоступное действие — `disabled` (Bot API 10.3).
- **Эмодзи:** не больше одного в строке. Анимированные — только в трёх местах: ожидание, успех, ошибка (§6.4).
- **Каждая ошибка отвечает на два вопроса:** где сейчас деньги клиента и что ему делать дальше.
- **Ссылка на чек выплаты.** Её может забрать любой, у кого она есть, поэтому в итоге всегда строка «Забрать чек может любой, у кого есть ссылка, — не пересылайте её».

Плейсхолдеры `{e_wait}` и подобные раскрываются в `<tg-emoji emoji-id="…">⏳</tg-emoji>`, если у владельца бота есть Premium (§6.4), иначе в обычный эмодзи. `{order}` — публичный номер заявки (`orders.public_id`, 10 символов). Суммы — строкой из `Decimal` без незначащих нулей, кроме двух знаков у USDT.

Фолбэк — строки списком в `<blockquote>`, правила — в `<blockquote expandable>`. Клавиатура: `[🔒 Конфиденциальность]` (callback `privacy`).

#### S4. «Обменять чек» → направление → инструкция

Экран меню «Обменять чек»: по строке на направление с текущей комиссией и лимитами (или «на паузе, сейчас не принимаю»), внизу — «Курс 1:1. Выплата — чеком другого кошелька: забрать его можно одной кнопкой». Клавиатура: `[CryptoBot → xRocket]` (`style: "primary"`, callback `dir:cb_to_xr_check`) · `[xRocket → CryptoBot]` (`dir:xr_to_cb_check`).

После выбора направления — инструкция:
```html

Пришлите сюда чек CryptoBot на сумму от <code>{min}</code> до <code>{max}</code> USDT.
Комиссия {fee}, минимум <code>{min_fee}</code> USDT. Взамен — чек xRocket.

Подойдёт чек в USDT для одного человека — без пароля, капчи и подписок.
```
Клавиатура: `[Как создать чек]` (callback `howto:<направление>`) · `[Отмена]`. Экран «Как создать чек» — шаги инлайн-режима (`@send 10usdt` / `@xrocket 10`) и запасной путь через меню кошелька (`/checks` → «Создать чек» → USDT → сумма; `/cheques` → «Персональный» → «Создать чек» → USDT → сумма), кнопка `[Открыть CryptoBot]` / `[Открыть xRocket]` (url).

`{fiat_line}` = `\n(= {fiat} по курсу CryptoBot с запасом 1 %; что останется — верну)`.

Клавиатура: `[Пришлю чек xRocket]` (callback `pay_check:{order}`, `style: "primary"`) · `[📋 Сумма]` (`copy_text: {x}`) · `[Отмена]` (без `style`). Клиент платит только чеком; оплаты нашим счётом нет.

Экран меню «Оплатить счёт» (до ссылки): что можно оплатить и за какую комиссию, пример ссылок `t.me/send?start=IV…` и `t.me/xrocket?start=inv_…`, «Оплачиваю одноразовые счета с суммой».

Клавиатура: `[📋 Сумма]` · `[Отмена]`.

Недоплата:

Клавиатура: `[📋 {rest}]` (`copy_text`) · `[Вернуть деньги]` (`style: "danger"`, callback `refund:{order}`).

## 7. Админ-панель

### 7.1. Где живёт

Админка и логи вынесены в **отдельного служебного бота** (ops-бот, свой токен, тот же процесс). Почему:

1. **Темы.** Режим тем в личных чатах включается **на весь бот** (`User.has_topics_enabled` — «True, if the bot has forum topic mode enabled in private chats» [проверено]). У клиентского бота это изменило бы интерфейс всем клиентам.
2. **Изоляция.** Утечка или перехват клиентского токена не даёт доступа к админке.
3. **Фильтр.** Ops-бот молча игнорирует всех, кого нет в `staff`.

Отвергнутая альтернатива — команды `/admin` в клиентском боте: смешивает аудитории, а для логов нужны темы.

Для команды из нескольких человек вместо личных чатов можно использовать приватную супергруппу-форум с ops-ботом-админом (`can_manage_topics`); темы там общие.

### 7.2. Роли и права

- пауза юзербота на время ручных действий в служебном аккаунте;
- отчёт о незабранных чеках выплаты.

### 7.4. Двойное подтверждение

1. Кнопка действия → сообщение-предпросмотр «Что произойдёт: … Сумма: … Необратимо: да/нет» с `[Подтвердить]` (`style: "danger"`) и `[Отмена]`.
2. В `callback_data` — одноразовый nonce: хранится на сервере, живёт 60 с, привязан к сотруднику и действию. Старые кнопки после рестарта или повторного нажатия не срабатывают.
3. Для самых опасных действий после кнопки нужно ввести контрольную строку. Таких действий пять:
   - выплата сверх потолка (контрольная строка — номер заявки);
   - «закрыть без выплаты» (номер заявки);
   - добавление адреса в белый список (последние 6 символов адреса);
   - смена ролей (слово `ПОДТВЕРЖДАЮ`);
   - выключение стоп-крана (слово `ПОДТВЕРЖДАЮ`).
4. Запись в `admin_audit` с `double_confirmed = true`. Копия события — в тему «Действия админов».

## 8. Логи и алерты владельцу

### 8.1. Темы ops-бота и уровни

| Тема (`createForumTopic` в личном чате ops-бота) | Что туда идёт |
|---|---|
| 🔁 Обмены | INFO: каждая завершённая заявка (в дайджесте), отказы и возвраты |
| 🚨 Ошибки | WARN/CRITICAL: `MANUAL_REVIEW`, задачи «оплати счёт вручную», неизвестные ответы кошельков, FLOOD_WAIT и отказы юзерботов, автопаузы |
| 💰 Резервы | Пороги, перекос, планы и итоги ребалансировки, вывод прибыли, сверки |
| 🛡 Безопасность | Новые авторизации аккаунтов, расхождение «реальный < леджер», подозрительные пользователи, неудачные попытки доступа к ops-боту |
| 👤 Действия админов | Каждая запись `admin_audit` |
| 📊 Сводки | Ежедневная сводка в 09:00 по времени владельца, еженедельная по понедельникам |

| Уровень | Доставка | Повтор |
|---|---|---|
| INFO | В дайджест раз в 5 мин или по 20 событиям; тихо (`disable_notification`) | — |
| NOTICE | Сразу, тихо | — |
| WARN | Сразу, со звуком (в тихие часы 00–08 — тихо) | Дедуп 15 мин по `dedup_key`: вместо нового сообщения правим старое («×7, последнее 14:05») |
| CRITICAL | Сразу, со звуком всегда | Каждые 15 мин, пока кто-то не нажмёт `[Принял]` (`alerts.acked_by`) |

**Защита от флуда.** Лимиты Bot API — ориентировочно 1 сообщение в секунду в чат [допущение: общий FAQ Telegram, проверить по 429 и `retry_after`]. Поэтому:

- у отправителя алертов своя очередь с токен-бакетом 1/с на чат;
- `retry_after` соблюдается;
- события одного `dedup_key` склеиваются;
- при очереди > 50 событий INFO и NOTICE сворачиваются в одно «N событий пропущено, см. /dash».

**Маскирование:** `start_param` чеков и ссылки на созданные чеки → `CQ12…9F`; суммы не маскируем; токены, сессии, `CRYPTOBOT_PIN` и номера телефонов не попадают в события в принципе — секреты лежат в `secrecy::SecretString`, у которого нет `Display` (§11.1).

## 9. Статистика и дашборды

### 9.1. Метрики и формулы

Период `P` = [начало, конец), время — UTC в БД, вывод — в часовом поясе владельца. Ниже `C` — множество заявок в состоянии `COMPLETED`, созданных в `P`.

| Метрика | Формула |
|---|---|
| Оборот (вход) | `Σ intake_amount` по `C` |
| Оборот (выход) | `Σ payout_amount` по `C` (для оплаты счёта — сумма счёта) |
| Число обменов | `|C|`, по направлениям |
| Валовая прибыль | `Σ` кредитовых проводок по `revenue:*` за `P` (комиссии + переплаты ниже порога + остаток фиатного буфера) |
| Чистая прибыль | валовая − `Σ` дебетовых проводок по `expense:*` (сеть, комиссии платформ, потери, рефералка) − постоянные затраты · дней в `P` / 30 |
| Средний чек | оборот (вход) / `|C|`; дополнительно медиана |
| Конверсия «ссылка → обмен» | `|C| / |заявки, кроме отклонённых как «не ссылка»|` |
| Конверсия «котировка → оплата» | заявки на оплату счёта, дошедшие до `RECEIVED` / все, дошедшие до `AWAITING_FUNDS` |
| Конверсия «/start → первый обмен» | пользователи с `first_completed_at` в `P` / пользователи с `created_at` в `P` |
| Доля ошибок | (`INTAKE_FAILED` + попадания в `MANUAL_REVIEW`) / все заявки `P` |
| Доля возвратов | `REFUNDED / (COMPLETED + REFUNDED)` |
| Время обработки | p50, p95 по `finished_at − created_at` для `C`, отдельно обмен и оплата счёта; дополнительно по шагам: приём (`activate_check`), создание чека (`create_payout_check`, отдельно инлайн и меню), задержка ответа бота кошелька |
| Незабранные чеки | число и сумма чеков выплаты и возврата без уведомления «Ваш чек активировал» старше 1, 3, 7 дней |
| Ручная оплата счетов | число задач `NeedsHuman`, медиана времени до «Оплачено» |
| Время ручного разбора | медиана и максимум от входа в `MANUAL_REVIEW` до выхода |
| Новые пользователи | `first_completed_at ∈ P` |
| Вернувшиеся | есть заявка в `C` и `first_completed_at < начала P` |
| Резервы | `A(w)` сейчас, минимум за `P`, время ниже `low` |
| Перекос | `skew` сейчас, среднее за `P` |
| Доступность направления | `1 − (минуты на паузе / минуты P)` |

Источник — `stats_daily` (материализованное представление, `REFRESH … CONCURRENTLY` раз в 5 мин) плюс онлайн-запрос за «сегодня». Деньги — из леджера, а не из полей заявки: так статистика совпадает со сверкой.

## 10. Архитектура на Rust

### 10.1. Процесс и задачи tokio

Один бинарник `exch`, один процесс, многопоточный рантайм tokio. Отвергнутая альтернатива — микросервисы (бот, движок, юзербот отдельно): на объёмах до сотен заявок в день это лишняя сеть и распределённые транзакции без выигрыша. Модульные границы всё равно проводим крейтами, чтобы при росте вынести юзербот в отдельный процесс.

| Задача | Запуск | Что делает | Ключевые параметры |
|---|---|---|---|
| `client_bot` (`tgbot`) | 1 | Long polling `getUpdates` клиентского бота через `botapi`, разбор, маршрутизация в движок; один чат обрабатывается строго последовательно (keyed mutex по `chat_id`), разные — параллельно | `timeout = 30 с`, `allowed_updates = [message, callback_query]` |
| `ops_bot` (`ops`) | 1 | То же для ops-бота: админка, кнопки алертов; игнорирует всех вне `staff` | — |
| `engine` | 1 | Драйвер FSM: события (ссылка, результат юзербота, таймер, решение оператора) → переход и эффекты (операции, hold, проводки) в одной транзакции | события через `mpsc(1024)`; `LISTEN orders_changed` |
| `outbox` | 1 | Берёт `operations` в `pending` (`FOR UPDATE SKIP LOCKED`), будится через `LISTEN operations_new` (без задержки поллинга) и раз в 1 с; ставит `dispatched` (коммит), отдаёт операцию в очередь актора нужного аккаунта, пишет результат и шлёт событие в FSM | §10.5 |
| `userbot[account]` | по 1 на аккаунт | Актор: владеет `UserbotWallet<GrammersTransport>`, очередь команд, **одно денежное действие в полёте**, поток апдейтов, сохранение каждого сообщения бота кошелька и «Избранного» в `wallet_messages`, корреляция ответа с командой, FLOOD_WAIT, переподключение, пауза по команде из `/ub` | `governor`: 1 действие / 1,5 с и ≤ 6–8 сообщений боту в минуту; таймаут ответа 30 с |
| `reconciler` | 1 | Сверка каждого кошелька раз в 15 мин и после каждых 10 заявок; проверка `payable` по терминальным заявкам | §4, П14 |
| `reserves` | 1 | Раз в 60 с: доступные резервы, перекос, ценовой рычаг, автопаузы | §3 |
| `timers` | 1 | Раз в 5 с: истёкшие котировки (`quote_ttl_seconds`), таймаут `INTAKE_UNKNOWN`, SLA разбора и задач «оплати счёт вручную» | индекс по дедлайнам |
| `alerts` | 1 | Очередь событий → ops-бот, токен-бакет 1/с на чат, агрегация и дедуп | §8 |
| `stats` | 1 (M7) | `REFRESH MATERIALIZED VIEW CONCURRENTLY stats_daily` раз в 5 мин, сводки | — |
| `heartbeat` | 1 | Пинг healthchecks.io раз в 60 с, **только если** `engine` и `outbox` обновили «пульс» за последние 2 мин | сторожевой таймер |

Входящих соединений у процесса нет: оба бота работают через long polling, вебхуков кошельков нет. Наружу открыт только SSH (§12).

**Надзор** (`app::supervisor`, уже есть): каждая задача завёрнута в супервизор. Паника или выход задачи → CRITICAL и перезапуск с backoff (1 → 60 с). Больше 5 перезапусков за 10 минут → `process::exit(1)`: Docker перезапустит контейнер, а рестарт-рекавери (§4, П16) доведёт заявки.

**Мягкая остановка** (SIGTERM, `stop_grace_period: 90s`):

1. `CancellationToken` → закрыть приём новых ссылок;
2. дать операциям в полёте до 60 с;
3. всё, что не успело, остаётся в `pending`/`dispatched` и после старта довозится по правилам П16.

Отмена future посреди денежного действия безопасна: статус `dispatched` закоммичен **до** отправки, а выводящая деньги операция после рестарта не повторяется, а сверяется.

**Бюджет задержки горячего пути** (цель p50 ≤ 15 с от ссылки до чека выплаты):

| Шаг | Время |
|---|---|
| Разбор и транзакция | < 20 мс |
| Пробуждение outbox через NOTIFY | < 5 мс |
| `/start` и ответ кошелька | 1–5 с (основная часть) |
| Транзакция `RECEIVED` + `PAYOUT_PENDING` | < 20 мс |
| Инлайн-запрос, отправка в «Избранное», ссылка из кнопки | 2–10 с [допущение: замерить в M2.3] |
| Правка сообщения клиенту | 0,1–0,3 с |

Активация и создание чека идут разными аккаунтами, поэтому пауза `governor` между ними не складывается. Запрещено: блокирующий код в async (тяжёлая отрисовка графиков — `spawn_blocking`), поллинг с фиксированной задержкой на горячем пути, лишние запросы к ботам кошельков до выплаты (баланс берём из леджера, сверка — отдельно).

### 10.4. Деньги

**Правила:**

1. Только `rust_decimal::Decimal`. В `clippy.toml` — `disallowed-types = ["f32", "f64"]` для всего workspace.
2. В БД — `NUMERIC(38,18)`, в JSON — **строки**. Сумму для бота кошелька (`@send 97.5usdt`, `@xrocket 97.5`, ввод суммы в меню) форматируем сами: точка, без незначащих нулей, уже на шаге выплаты [допущение M0: формат ввода суммы у ботов].
3. Тип `Money { amount, asset }`: сложение разных активов — ошибка. Отрицательные суммы в `Money` запрещены, знак есть только в проводке.
4. Сумму из текста кошелька разбираем так: нормализация пробелов и разделителей → `Decimal::from_str_exact` → проверка масштаба ≤ точности платформы.

**Точность и округление:**

| Что | Правило | Стратегия `rust_decimal` |
|---|---|---|
| Выплата клиенту | вниз до `payout_step` (USDT 0,01; TON 0,001) | `RoundingStrategy::ToZero` |
| Комиссия | `amount_in − payout`, остаток округления — в пользу сервиса | — |
| Сумма «к оплате» в котировке | вверх до шага | `AwayFromZero` |
| Пересчёт фиата | вверх до шага после буфера | `AwayFromZero` |
| Комиссия с рычагом | вверх до 0,01 п.п. | `ToPositiveInfinity` |
| Отображение | без округления: значение уже на шаге; USDT всегда 2 знака | — |

**Леджер (двойная запись, `domain::ledger`).** Счета: `asset:<cb|xr>:<ASSET>` (личный баланс аккаунта юзербота), `asset:transit:<ASSET>`, `liability:payable:<ASSET>` (деньги клиентов в заявках), `liability:referral:<ASSET>`, `revenue:fee|excess|fx_buffer:<ASSET>`, `expense:network_fee|platform_fee|loss|referral:<ASSET>`, `equity:capital|owner_withdrawals:<ASSET>`. Знак: дебет > 0, кредит < 0. Каждая проводка сбалансирована по активу — это проверяют шаблоны в коде и отложенный триггер в БД (тесты `crates/storage/tests/invariants.rs`).

| Событие (обмен CryptoBot → xRocket и оплата счёта CryptoBot) | Проводка |
|---|---|
| Активирован чек клиента CryptoBot 100 USDT | Дт `asset:cb` 100 / Кт `liability:payable` 100 |
| Создан чек выплаты xRocket 97,50 | Дт `liability:payable` 100 / Кт `asset:xr` 97,50 / Кт `revenue:fee` 2,50 |
| Создан чек возврата 100 (на платформе входа) | Дт `liability:payable` 100 / Кт `asset:cb` 100 |
| Счёт CryptoBot оплачен: клиент прислал чек xRocket X = 10,30, счёт A = 10,00 | вход: Дт `asset:xr` 10,30 / Кт `liability:payable` 10,30; оплата: Дт `liability:payable` 10,30 / Кт `asset:cb` 10,00 / Кт `revenue:fee` 0,30 |
| Переплата оставлена | Дт `liability:payable` e / Кт `revenue:excess` e |
| Переплата возвращена чеком | Дт `liability:payable` e / Кт кошелёк входа e |
| Ребалансировка | отправка: Дт `asset:transit` / Кт `asset:cb`; комиссия: Дт `expense:network_fee` / Кт `asset:cb`; поступление: Дт `asset:xr` / Кт `asset:transit` |
| Взнос капитала / вывод прибыли | Дт `asset:*` / Кт `equity:capital`; Дт `equity:owner_withdrawals` / Кт `asset:*` |
| Заморозка (провизия) | Дт `expense:loss` / Кт `asset:*` (сторно при разблокировке) |

Деньги списываются с нашего баланса в момент создания чека, тогда же делаем проводку выплаты. Комиссия признаётся **в момент выплаты**: возврат — простое сторно `payable` без отмены дохода. Инвариант сверки: по каждой терминальной заявке сумма проводок по `liability:payable` с её `order_id` = 0, по нетерминальной — равна полученному.

### 10.5. Надёжность

**10.5.1. Машина состояний.** `domain::fsm`:

- `transition(flow, state, event) -> Result<Transition { to, effects }, FsmError>` — единственный способ сменить состояние; эффекты: `Operation { kind, role }`, `Hold(Place | ShrinkToPayout | Release | Consume)`, `Post(Intake | Payout | InvoicePaid | Refund | ManualClose)`; уведомление клиента — не эффект FSM, `tgbot` подписан на события движка;
- 16 состояний, 31 переход; исчерпывающий тест (поток × состояние × событие) проверяет, что достижимые переходы = `ALLOWED`, а тест `storage` — что `ALLOWED` = `order_state_transitions` в БД;
- обновление заявки — `UPDATE … WHERE id = $1 AND version = $2`; 0 строк → перечитать и повторить решение.

**10.5.2. Идемпотентность.** Ключ операции — `operations.idempotency_key` (8–50 символов, уникален):

| Операция | Ключ |
|---|---|
| Выплата | `ord-<id>-payout` |
| Возврат | `ord-<id>-refund` |
| Возврат переплаты | `ord-<id>-excess` |
| Активация (n-й чек заявки) | `ord-<id>-intake-<n>` |
| Оплата счёта | `ord-<id>-pay` |
| Ребалансировка | `rb-<id>` |
| Повторная выплата по решению оператора | `ord-<id>-payout-2` |

Ключ — наша метка: уникальный индекс не даст создать вторую строку outbox. Кошелёк его не видит [допущение M0: если у чека есть комментарий — пишем ключ туда, это упростит `find_issued_check`]. Идемпотентность на стороне Telegram даёт `random_id`:

- `random_id` (i64) генерируется при создании операции и хранится в `operations.request` до первой отправки;
- повтор отправки внутри попытки (после `Timeout` или `Disconnected`) — только с ним: сервер вернёт прежнее сообщение или `RANDOM_ID_DUPLICATE` (`TransportError::RandomIdDuplicate` значит «уже отправлено, ждём ответ»);
- `mtproto` отправляет ровно данный `random_id` и сам ничего не повторяет;
- новый `random_id` — только у новой операции: «Повторить выплату» оператора создаёт новую строку outbox;
- входящие обновления Bot API дедуплицируются по `update_id`; сообщения ботов кошельков — по `(userbot, bot, message_id, edit_date)` в `wallet_messages`.

**10.5.3. Outbox.** Изменение состояния и вставка операции — одна транзакция. Воркер:

1. помечает операцию `dispatched`, `attempts + 1` (коммит);
2. вызывает `WalletBot` нужной платформы через очередь актора аккаунта;
3. результат (`succeeded` / `failed` / `unknown`, `response`, `external_id` — ссылка на чек) записывает в той же транзакции, что и следующий переход заявки.

Между шагами процесс может упасть в любой точке — разбор каждой точки в §4.20.

**10.5.4. Повторы.**

| Ситуация | Решение |
|---|---|
| `BotError::FloodWait`, `BotError::Unavailable`: операция не начиналась | назад в `pending` с `next_attempt_at`; попытка не тратится |
| `activate_check`: таймаут транспорта | повтор отправки с тем же `random_id`, ждём ответ; нет ответа 30 с → `Unknown` → сверка |
| `activate_check`: xRocket «не найден» на чеке моложе 3 с | один повтор |
| `open_invoice`, `read_balance` | повтор с экспоненциальным backoff и полным джиттером: `sleep = rand(0, min(60 с, 1 с · 2^attempt))`, до `max_attempts` |
| Операция, выводящая деньги: любой неясный исход | **без повторов**: `unknown` → сверка (`find_issued_check`, статус счёта, баланс) → событие или `MANUAL_REVIEW` |
| `AccountRestricted`, `NotAuthorized` | автопауза направлений (П15), CRITICAL |

`max_attempts = 1` для `create_payout_check`, `create_refund_check`, `create_excess_check`, `pay_invoice`, `withdrawal` закреплено в схеме: `CHECK (kind IN ('activate_check', 'open_invoice', 'read_balance') OR max_attempts = 1)`.

**10.5.5. Таймауты.**

| Вызов | Таймаут |
|---|---|
| Bot API | 10 с (`getUpdates` — 35 с) |
| RPC MTProto (`sendMessage`, `sendInlineBotResult`, нажатие кнопки) | 10 с, затем `Timeout` — исход неизвестен |
| Ответ бота кошелька | 30 с |
| Ссылка в сообщении-чеке (правка заглушки) | до 15 с [допущение: lovec опрашивает инлайн-сообщения до 15 с] |
| PostgreSQL | `statement_timeout = 5 с`, `idle_in_transaction_session_timeout = 10 с` |
| Мягкая остановка | 60 с |

**10.5.6. FLOOD_WAIT и очередь аккаунта.** Актор аккаунта держит две очереди: деньги клиентов (приоритет) и служебные (балансы, канарейки, сверки). Обе — `mpsc(100)` с `biased select`. Одно действие в полёте. `governor` — не чаще 1 действия в 1,5 с и не больше 6–8 сообщений боту в минуту.

- `FLOOD_WAIT_X` → пауза всего аккаунта на X с; вызовы до её конца сразу получают `BotError::FloodWait`.
- X > 300 → аккаунт `flood_wait`, автопауза направлений и CRITICAL. Рестарт паузу не снимает [проверено: lovec AUDIT-2.md:1787-1791].
- Переподключение MTProto — с backoff. После него — догон апдейтов (`getDifference`) и `getHistory` по чатам с кошельками и «Избранному» с курсора `wallet_chat_cursors`.

**10.5.7. Корреляция ответа.** Подписка на поток (`Transport::subscribe`) — до отправки. Ответ — первое сообщение закреплённого бота с id больше id нашей команды; правки того же сообщения переклассифицируют ответ; промежуточное «обработка» ждёт дальше; «Ваш чек активировал» и входящие переводы не закрывают ожидание. Таймаут 30 с → `Unknown`. Каждое сообщение сохраняется в `wallet_messages` с `operation_id` **до** разбора. Сообщения без ожидающей команды тоже сохраняются и разбираются как «спонтанные» — для сверки и отчёта о незабранных чеках. Для инлайн-чека ждём сообщение в «Избранном» через бота кошелька (`via_bot`) с URL-кнопкой; если кнопки ещё нет — ждём правку.

**10.5.8. Рестарт-рекавери** — §4, П16.

**10.5.9. Сверка** — §4, П14.

**10.5.10. Канарейка.** Раз в час актор отправляет каждому кошельку безопасную команду (открыть «Кошелёк») и прогоняет ответ через классификатор. Незнакомый ответ → WARN «интерфейс кошелька изменился» **до того**, как пострадает живая заявка.

### 10.6. Разбор ответов кошельков

- **Структура:** `crates/parsers/src/replies.rs` (классификатор ответов на `/start`, карточка счёта, ответ на оплату, баланс, созданный чек), `links.rs`, `amount.rs`; фикстуры — `crates/parsers/tests/fixtures/*.json`: текст, сущности, кнопки, ожидаемый класс и извлечённые поля. Сейчас фикстуры синтетические, по словарям lovec; настоящие тексты даст режим записи `exch record` (M2.3) и пилот (M6).
- **Алгоритм:**
  1. нормализация (NFKC, нижний регистр, схлопывание пробелов, удаление эмодзи);
  2. упорядоченные правила-словари и регулярки с именованными группами (порядок проверок — как в lovec: «неверный пароль» раньше «пароль», «ваш чек активировал» раньше «получено»);
  3. ровно одно сработавшее правило → результат;
  4. ноль или больше одного → `Unknown`.
- **Версия формата** (`parser_version`, например `cb-2026.10`) пишется в `wallet_messages`. Новая версия добавляется рядом со старой: классификатор пробует версии от новой к старой, а статистика по версиям показывает, когда старую можно удалять.
- **Автопауза:** любой `Unknown` в денежной операции →
  - операция `unknown`;
  - заявка — в сверку или `MANUAL_REVIEW`;
  - направления этого кошелька — `auto_paused` с причиной «незнакомый ответ», снимается только вручную;
  - CRITICAL с замаскированным текстом;
  - `/unknown` в ops-боте превращает сообщение в фикстуру.
- **Правило:** словарь не подгоняем под один текст. Новый текст — новая фикстура и правило, которое не пересекается с другими классами (CLAUDE.md, правило 13).
- **Золотые тесты:** каждая фикстура — тест. CI падает, если правило матчит две фикстуры разных классов.

### 10.7. Схема БД и миграции

- **Схема** — [`schema.sql`](schema.sql): 28 таблиц, представление `wallet_available`, материализованное представление `stats_daily`. Инварианты I1–I6 и охрана переходов проверяются тестами `crates/storage/tests/invariants.rs` на живом PostgreSQL (`sqlx::test`). `schema_test.sql` частично v0.1; его заменяют эти тесты, файл можно удалить (HANDOVER §3).
- **Ключевые индексы и CHECK:**
  - `orders_intake_param_live` — один чек → одна живая заявка;
  - `orders_invoice_param_live`, `orders_invoice_param_completed` — чужой счёт в работе один раз, оплаченный больше не принимаем;
  - `operations_one_settle_per_order`, `operations_one_excess_refund_per_order` — не больше одной расчётной операции и одного возврата переплаты на заявку;
  - `operations_check_once`, `operations_invoice_pay_once` — один чек активируется одной операцией, один счёт оплачивается одной операцией;
  - CHECK `max_attempts = 1` для операций, выводящих деньги;
  - `ledger_tx_once_per_operation`;
  - `operations_due` (очередь outbox), `orders_live_state` (рекавери), `holds_active_wallet` (резервы), `wallet_accounts_one_active`.
- **Миграции:** `schema.sql` = `migrations/0001_init.sql` байт в байт (тест сверяет), `sqlx::migrate!()` встроены в бинарник и применяются при старте **до** открытия приёма. Вручную схема применяется так: `psql -1 -f schema.sql` (в файле нет `BEGIN/COMMIT`).
  - Пока проект не задеплоен, схема меняется правкой `0001`. После первого деплоя — только новые миграции, только вперёд, каждая — в транзакции.
  - Изменения совместимы по схеме «расширить → перенести → сузить»: старый бинарник работает с новой схемой. Это нужно для отката без потери заявок.
  - Перед миграцией с удалением данных — ручной бэкап (§12).

## 11. Безопасность и тестирование

### 11.1. Безопасность

**Сессия юзербота — это прямой доступ к деньгам.** В v0.2 других ключей к деньгам нет: токенов платёжных API не существует, весь резерв — на личных балансах двух аккаунтов.

| Мера | Как |
|---|---|
| Шифрование | Сессия grammers (ключ авторизации, DC, пиры) → XChaCha20-Poly1305 (`mtproto::crypto`): ключ 32 байта из `SESSION_KEY` (base64), случайный 24-байтный nonce на каждое сохранение, AAD с меткой аккаунта, `key_version` в строке → `userbot_accounts.session_ciphertext`, `session_nonce`. Своя реализация `Session` (`mtproto::session`): открытый текст только в памяти (`Zeroizing`), на диск не пишется [проверено: в grammers 0.10 у хранилища в памяти нет экспорта — LOVEC-PORTING §8.6] |
| Вход | CLI `exch login --label ub-cb-1` **на сервере** по SSH (M2.2): телефон, код из Telegram, облачный пароль 2FA — из терминала (`mtproto::TerminalPrompt`); телефон в БД — только маской. На ноутбуке разработчика боевые сессии не создаются |
| 2FA и PIN | Облачный пароль Telegram на каждом аккаунте юзербота; PIN CryptoBot с резервной почтой (обязателен для выводов [проверено]). PIN — в переменной `CRYPTOBOT_PIN` только на сервере (Р4); резервная почта и пароли — в менеджере паролей владельца |
| Контроль сессий | Раз в 10 мин `account.getAuthorizations`: незнакомая авторизация → CRITICAL в «Безопасность» с кнопкой «Завершить» (`account.resetAuthorization`). Сессия Telegram Desktop для ручных действий оператора — известная, помечается в `/ub` |
| Ротация | Раз в квартал и при любом подозрении: новый вход, `auth.logOut` старой сессии, смена `SESSION_KEY` (перешифровка всех строк при `key_version + 1`); после любой утечки PIN — смена PIN |
| Гигиена аккаунтов | Выделенные аккаунты: руками ими не пользуются, кроме оговорённых случаев при остановленном юзерботе (П3, §3.5). Реальные SIM-номера, **не виртуальные** (по отзывам, CryptoBot блокирует аккаунты на виртуальных номерах [проверено: пересказ выдачи по vc.ru]); аккаунты с историей; приватность «никто» для сообщений, звонков и групп; юзербот пишет только закреплённым ботам кошельков и в «Избранное», ни на что не подписывается; свой `api_id` с my.telegram.org — чужие `api_id` официальных клиентов не используем |

**Секреты.**

- Где хранятся: только переменные окружения из `.env` на сервере (`chmod 600`, владелец root), копия — в менеджере паролей. Список переменных — §12, шаг 8, и `.env.example`. Секретов нет в промтах, в чатах с ИИ, в логах, в коммитах и в тестовых снимках.
- В коде: `secrecy::SecretString` (нет `Debug`/`Display`); тест `app::config` проверяет, что `Debug` конфига их не раскрывает.
- Логи: не попадают никогда. Интеграционный тест прогоняет сценарии с известными «секретами-метками» и ищет их в перехваченных логах и в БД — найдено → тест красный.
- HAR-запись оплаты счёта (M0) содержит PIN и токены мини-приложения: хранится вне репозитория, передаётся разработчику лично, после разбора удаляется, PIN меняется.

**Маскирование в логах.** Обёртка `Masked<T>` для `start_param`, ссылок на созданные чеки и адресов (`CQ12…9F`). Ссылка на чек выплаты — это деньги: в логах и алертах — только маской, целиком — только в `orders.payout_check_url` и в личке клиенту. Телефоны — только маской. Telegram ID пользователей не маскируем: это не секрет, а нужен для поддержки.

**Проверка админов.**

- Ops-бот работает только в приватных чатах. Проверяется `from.id ∈ staff` и `disabled_at IS NULL` на **каждом** апдейте — не только на `/start`.
- Роль проверяется на каждом действии.
- Одноразовые nonce в `callback_data` (§7.4).
- Неудачные обращения посторонних — тихий отказ и NOTICE в «Безопасность», не чаще раза в час на пользователя.

**Лимиты и антиабьюз.**

| Правило | Значение по умолчанию |
|---|---|
| Частота | 5 заявок за 10 мин, 10 ссылок в минуту на пользователя (`settings.user_rate_limit`, `governor`, ключ — `tg_user_id`) |
| Открытых заявок одновременно | 2 на пользователя |
| Дневной лимит | 1 000 $ (новичок до первых 3 успешных обменов — 200 $, разовая заявка — до `new_user_max_amount` = 100) (`settings.daily_limit_usd`) |
| Серия неудачных чеков | 5 подряд (`INTAKE_FAILED`) за час → автобан на 1 час с причиной (зондирование, ловля чеков) |
| Глобальный предохранитель | > 10 ошибок кошелька за 5 мин → пауза направления |
| Правила сервиса | «Курс и лимиты» (`/terms`): запрещённые источники средств, право отказать и вернуть |

**Сервер.** Только SSH-ключи, без входа root и паролей. `ufw` + облачный фаервол DO, входящий — только 22/tcp. `unattended-upgrades`. Контейнер приложения под непривилегированным пользователем с `read_only: true`. PostgreSQL наружу не публикуется.

## 12. Деплой и эксплуатация (пошагово)

Цель — сервер, который сам перезапускается, делает бэкапы, сообщает о проблемах и обновляется без потери заявок. Выбор: **Docker Compose** (приложение + PostgreSQL) на одном дроплете. Отвергнутые варианты:

- systemd + бинарник — проще отладка, но больше ручной настройки PostgreSQL и обновлений;
- управляемая база DigitalOcean (от ≈ 15 $/мес) — переход на неё при оптимистичном сценарии.

### Шаг 0. Учётные записи
DigitalOcean, GitHub (репозиторий приватный), healthchecks.io (бесплатно), хранилище бэкапов (DO Spaces 5 $/мес или Backblaze B2), менеджер паролей (Bitwarden или 1Password). Для юзерботов — два **выделенных** аккаунта Telegram на реальных SIM (CryptoBot и xRocket), `api_id`/`api_hash` с my.telegram.org (API development tools), PIN CryptoBot на аккаунте CryptoBot.

### Шаг 1. Ноутбук (Windows)
1. Установите Git for Windows, Rust (`rustup-init.exe`, вариант MSVC + Visual Studio Build Tools; версия 1.97 закреплена в `rust-toolchain.toml`), Docker Desktop, VS Code; `cargo install sqlx-cli --version 0.9.0 --locked --no-default-features --features postgres,rustls`.
2. PowerShell: `ssh-keygen -t ed25519 -C "exch-deploy"` — Enter на все вопросы и пароль на ключ. Публичный ключ: `type $env:USERPROFILE\.ssh\id_ed25519.pub`.
3. Локальная база для разработки: `docker run -d --name exch-pg -e POSTGRES_PASSWORD=dev -p 5432:5432 postgres:16`.

### Шаг 2. Дроплет

### Шаг 11. Мониторинг
- **healthchecks.io:** проверка с периодом 1 мин и grace 3 мин; уведомления в Telegram и на почту. Приложение пингует, только если `engine` и `outbox` живы (§10.1). Так ловятся и падение сервера, и «зависание».
- **DO Monitoring:** алерты CPU > 80 % 10 мин, диск > 80 %, память > 90 %.
- Внутренние алерты — §8.

### Шаг 12. Бэкапы
1. Ключ: `age-keygen -o key.txt` — **на ноутбуке**. Приватный ключ — в менеджер паролей, на сервер кладём только публичный (`age1…`).
2. Скрипт `/opt/exch/backup.sh`:
   ```bash
   set -euo pipefail
   HC_BACKUP_URL=https://hc-ping.com/<uuid-проверки-бэкапа>   # отдельная проверка healthchecks.io
   f=/var/backups/exch/exch-$(date -u +%F-%H%M).dump.age
   docker compose -f /opt/exch/docker-compose.yml exec -T db pg_dump -U exch -Fc exch | age -r age1… > "$f"
   rclone copy "$f" remote:exch-backups/ && find /var/backups/exch -mtime +3 -delete
   curl -fsS "$HC_BACKUP_URL" >/dev/null
   ```
3. systemd timer: ежедневно в 02:30 UTC. Хранение в бакете: 7 ежедневных, 4 еженедельных, 6 ежемесячных (правила жизненного цикла бакета).
4. **Раз в месяц — учебное восстановление:**
   ```bash
   age -d -i key.txt f.dump.age | pg_restore -d exch_restore_test
   ```
   затем `SELECT` контрольных сумм леджера.

### Шаг 13. Логи
Приложение пишет JSON в stdout. Docker ротирует (50 МБ × 5). Просмотр: `docker compose logs --since 1h exch | grep '"level":"ERROR"'`. Денежные события дублируются в БД (`order_transitions`, `operations`, `wallet_messages`). Логи — для отладки, а не единственная запись.

### Шаг 14. Обновление без потери заявок
1. `/maint on 5 Обновление` в ops-боте: новые ссылки не принимаются.
2. Дождаться, пока `/dash` покажет «в полёте: 0». Обычно < 1 мин; если долго — можно не ждать, рекавери доведёт.
3. Обновить образ:
   ```bash
   sed -i 's/^EXCH_IMAGE=.*/EXCH_IMAGE=ghcr.io\/<you>\/exch:<new-sha>/' .env
   docker compose up -d
   ```
   SIGTERM, мягкая остановка до 60 с, затем рекавери.
4. `/selftest` → `/maint off`.
5. **Откат:** вернуть прежний `EXCH_IMAGE` и `docker compose up -d`. Миграции совместимы назад (§10.7).

### Шаг 15. Ежедневная эксплуатация (5 минут)
`/dash`: резервы в зелёной зоне, очередь разбора пуста, сверка ok, юзерботы `active`. Сводка в «Сводках». Вывод прибыли — по предложению бота.

### Шаг 16. Авария
Сервер потерян:

1. новый дроплет — шаги 2–8;
2. восстановить последний бэкап (сессии юзерботов в БД зашифрованы, ключ — в `.env` из менеджера паролей);
3. запуск в режиме обслуживания;
4. полная сверка всех кошельков;
5. разбор расхождений;
6. открыть приём.

Цели: RPO ≤ 24 ч (бэкап) — фактически меньше, потому что в кошельках и Telegram остались первичные данные для сверки; RTO ≤ 2 ч.
